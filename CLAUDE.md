# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A headless e-commerce storefront ("Fashion Store") built with Nuxt 4.6.3 against a Medusa.js commerce backend. It is based on https://github.com/OlivierBelaud/nuxt-starter-medusa. Requires a supported Nuxt Node.js version (`^22.22.3 || ^24.15.0 || >=26.0.0`) and pnpm >= 9 (pinned to 11.5.0 by `packageManager`), plus a running Medusa backend.

## Commands

```bash
pnpm install       # install deps (postinstall runs `nuxt prepare`)
pnpm dev           # start dev server
pnpm build         # production build
pnpm generate      # static generation
pnpm preview       # preview a production build
pnpm lint          # eslint .
pnpm lint:fix      # eslint . --fix
pnpm format        # prettier --write .
pnpm format:check  # prettier --check .
pnpm test          # vitest run --typecheck
pnpm test:e2e      # playwright test (builds the app, see "Test runner boundary")
```

Vitest has two projects. The plain `unit` project (`tests/unit/`) runs under jsdom without booting Nuxt; keep pure utilities, types, services and server helpers here. The `nuxt` project (`tests/nuxt/`) uses `@nuxt/test-utils`' Nuxt environment for composables, middleware and components that need auto-imports, plugins, injections or registered components. Use `mountSuspended` there instead of manually stubbing Nuxt UI or app components. `pnpm test` runs both projects; its TypeScript checker remains scoped to `tests/unit/` through `tsconfig.test-unit.json`, while `pnpm lint` checks both test trees. Run a specific test with `pnpm exec vitest run --project unit tests/unit/utils/product.test.ts` or `pnpm exec vitest run --project nuxt tests/nuxt/composables/cms.test.ts`. The Nuxt test app loads the real Nuxt UI and i18n modules, but excludes Medusa, Sentry, image and sitemap modules. Repository/service boundaries are mocked so tests never call Medusa, Payload or Stripe; no credentials or backend are required.

The Playwright e2e suite (`tests/e2e/`, `playwright.config.ts`) is separate from both Vitest projects and from `pnpm test`; see "Test runner boundary" for how it runs. After `pnpm install` run `pnpm exec playwright install chromium` once to get the browser (CI installs it with `--with-deps`).

CI has two workflows. `.github/workflows/ci.yml` runs `pnpm test`, `pnpm lint`, `pnpm format:check` and `pnpm build` on pushes to `main` and pull requests. `.github/workflows/e2e.yml` runs `pnpm test:e2e` (Chromium on pull requests and `main`; Firefox and WebKit through a manual `workflow_dispatch` with `all_browsers`) on Node 22, and uploads the HTML report and the traces/screenshots for 7 days. It is deliberately not a required check yet, so a slow or flaky browser run can't block a merge; make it required in the branch protection rules once it is stable.

### Environment

Copy `.env.template` to `.env` and set:

- `NUXT_PUBLIC_MEDUSA_BACKEND_URL` — Medusa backend base URL (default `http://localhost:9000`)
- `NUXT_PUBLIC_MEDUSA_PUBLISHABLE_KEY` — Medusa store publishable API key
- `NUXT_PUBLIC_STRIPE_KEY` — Stripe publishable key
- `NUXT_PUBLIC_INPOST_GEOWIDGET_TOKEN` — InPost Geowidget token for the parcel locker picker in the delivery step
- `NUXT_PUBLIC_PAYLOAD_URL` — Payload CMS base URL (editorial/marketing content; see Payload CMS integration below). All editorial content (header nav, footer links/contact, home sections and their images) comes only from Payload; there is no static fallback, so the sections that need it are not rendered while it is unset or unreachable.
- `NUXT_PUBLIC_SITE_URL` — public origin of the storefront (e.g. `https://shop.example.com`), read by `nuxt-site-config` (installed by `@nuxtjs/sitemap`) for canonical/hreflang links, `sitemap.xml` and `robots.txt`. Optional — falls back to the request origin, so set it in production to keep preview/alias hosts out of canonical URLs.
- `NUXT_PUBLIC_SENTRY_DSN` — Sentry DSN (public by design; see Error reporting). Optional: empty means Sentry is off and errors only go to the console. Use the same Sentry organization as the Medusa backend and admin (damiankrupa1/medusaDemo#18), as its own project. Related, all optional: `SENTRY_DSN` (server-only DSN, defaults to the public one), `NUXT_PUBLIC_SENTRY_ENVIRONMENT` (defaults to Vercel's `VERCEL_ENV`, then `NODE_ENV`), `NUXT_PUBLIC_SENTRY_RELEASE` (defaults to `VERCEL_GIT_COMMIT_SHA`), `NUXT_PUBLIC_SENTRY_TRACES_SAMPLE_RATE` (0-1; empty keeps tracing off).
- `SENTRY_ORG`, `SENTRY_PROJECT`, `SENTRY_AUTH_TOKEN` — build-time only, for the source map upload. Keep them in Vercel/CI secrets, never as `NUXT_PUBLIC_*`. Without `SENTRY_AUTH_TOKEN` no source maps are generated or uploaded.

Several of these are read by `nuxt.config.ts` when the app is **built**, not when it starts, so changing them needs a new build: the Medusa URL and publishable key (`medusa.baseUrl`/`publishableKey`), the `@nuxt/image` host allow-list (`NUXT_PUBLIC_PAYLOAD_URL` + `NUXT_PUBLIC_PAYLOAD_IMAGE_HOSTS`) and the Sentry release and source map settings. The `runtimeConfig.public.*` values (`stripeKey`, `payloadUrl`, Sentry DSN) are baked in as defaults and can still be overridden by the same variable at runtime. A `.env` file only fills variables that are undefined, so a variable set to an empty string in the environment wins over it. The e2e suite relies on that (see "Test runner boundary").

### Git hooks (husky)

- `pre-commit` runs `pnpm lint` (`eslint .` on the whole project, not only staged files) and blocks the commit on failure. That is all it does: `package.json` has a `lint-staged` config (`eslint --fix` + `prettier --write` on `*.{js,ts,vue}`, `prettier --write` on `*.{json,css,scss,md}`), but no hook calls it, so nothing formats or auto-fixes staged files. Run `pnpm format:check` / `prettier --write <files>` yourself.
- `commit-msg` runs commitlint (`@commitlint/config-conventional` + `commitlint.config.js`). Commit subjects must use `type: description` with `type` restricted to `feat|fix|refactor|docs|style|test|build`, a non-empty subject, max 72 chars. The hook prints commitlint's errors but does not block the commit (the script ends without `exit 1`, so it always exits 0), so check its output yourself.

## Architecture

### Three-layer data access: repository → service → composable

Most Medusa Store API access flows through three layers under `app/`:

1. **Repository** (`app/repository/*.repository.ts`): thin data-access functions. `apiRepository()` wraps `useMedusaClient()` (from `@nuxtjs/medusa`) with a `request()` helper that reports (`captureError`) and rethrows errors; the `product`, `category`, `collection`, `order`, `payment`, and `cart` repositories all call `apiRepository()` and issue `client.store.*` calls directly. `customer.repository.ts` and `country.repository.ts` are the exceptions: they call `server/api/customers/**` and `server/api/regions` via `$fetch` (still funneled through `apiRepository()`'s `request()`), because auth needs the server-side cookie session and regions are cached on the server. `stripe.repository.ts` wraps Stripe.js instead of Medusa (lazy `loadStripe`, card element, card/BLIK/Przelewy24 confirmations, PaymentIntent lookup) and turns Stripe's `{ error }` results into thrown errors, reporting all but the customer-side ones (`card_error`, `validation_error`).
2. **Service** (`app/services/*.service.ts`): composes repository calls and adds business logic. `cart.service.ts`, `customer.service.ts` and `payment.service.ts` carry real logic (cart-id lifecycle, region reconciliation, `refreshNuxtData` side effects; for payment, picking the Stripe confirmation by provider and checking the payment Przelewy24 redirected back from) and are consumed by composables. `category.service.ts`, `collection.service.ts`, `order.service.ts`, and `product.service.ts` are currently thin pass-throughs with **no callers** — the composables for those domains call the repository directly instead. If you touch one of those domains, either wire the composable through its service (so the layer earns its keep) or remove the unused service — don't add a fourth pattern (this is about `app/`; the server side has its own layers, below).
3. **Composable** (`app/composables/*.ts`): the Vue-facing layer. Wraps repository/service calls in `useLazyAsyncData`/`useLazyFetch` for reads (see cache-key convention below), or a `loading`/`data`/`mutate()` shape for writes.

**Server API routes** (`server/api/**`): Nitro/H3 handlers; `customers/**` build their `customerRepository(serverMedusaClient(event))` from `serverMedusaClient(event)` (from `#medusa/server`) and are wrapped in `defineWrappedResponseHandler` (`server/utils/handler.ts`), which catches thrown errors, extracts `MedusaError` `status`/`message`, and re-throws as an H3 error (an error that already is an H3 error, like a validation 400, passes through unchanged). Only `server/api/customers/**` (login/register/logout/me, for the server-side cookie session), `server/api/regions` (a `defineCachedEventHandler`, since the region middleware needs regions on every server render) and `server/api/cms/[slug]` (the Payload proxy, see Payload CMS integration; not Medusa, so it is not wrapped in `defineWrappedResponseHandler`) are called from `app/` today.

**Server layers** (`server/`): the same idea applies on the server, so a handler never talks to an external system itself.

- `server/repository/*.repository.ts`: one file per external boundary (Medusa, Payload). It alone knows that system's URL or SDK calls, normalises its input (e.g. trailing slashes), sets the timeout and maps an upstream failure to an H3 error. It reports an external system's failure itself, through `captureError()` like `apiRepository()` does (the Payload repository does it with `source: 'payload'` and the slug as `global`), and links the reported error as the `cause` of the H3 error it throws, so Sentry's Nitro hook doesn't report that H3 error again; the handler and the app side don't repeat it. It takes its configuration as arguments (`payloadRepository(baseUrl)`), so a test needs no runtime config. Nitro auto-imports only `server/utils`, so a handler imports it explicitly: `~~/server/repository/payload.repository`.
- `server/repository/customer.repository.ts` (Medusa auth + store customer, for `customers/**`) differs from the Payload one in two ways. It takes the request's SDK client, `customerRepository(serverMedusaClient(event))`, never a client shared at module level, and every call made as the customer takes the token as an argument. And it neither catches nor reports Medusa errors: its only callers are wrapped in `defineWrappedResponseHandler()`, which already reports a Medusa error once (`source: 'server-api'`) and keeps its status and message, so reporting in the repository would double it.
- `server/services/*.service.ts`: only when something composes several repository calls with logic. No pass-through services. None exists yet: login and register were the expected case, but they only hand the token from one Medusa call to the next and set the cookie in between, which is HTTP, so they stay two repository calls in the handler.
- Handlers (`server/api/**`) do HTTP only: `parseRequestInput`, cookies, status codes, cache options, then one repository or service call (login and register: two, with the session cookie set between them).
- Every server handler follows this since issue #43 (the Payload proxy, `regions`, `__sitemap__/urls` and `customers/**`). Don't write new handlers the old way.
- `medusaRepository(event)` (`server/repository/medusa.repository.ts`) wraps `serverMedusaClient(event)` for `regions` (`listRegions()`) and the sitemap (`listSitemapCatalog()`, which walks products, categories and collections with `listAllPages`). It reports a Medusa failure once (`source: 'medusa'`; a 4xx stays a breadcrumb) and throws an H3 error with Medusa's status (500 without one) and the reported error as `cause`. Handlers that use it are therefore not wrapped in `defineWrappedResponseHandler`, which would report the same failure again. `customers/**` is wrapped on purpose, because `customerRepository()` does not report (see above).

- **Authenticated handlers** read the `medusa_jwt` cookie and pass it to `customerRepository()`, which sends it as `Authorization: Bearer <token>` (`me.get.ts`, `me.post.ts`); `me.post.ts` answers `401` before reading the body or touching Medusa when the cookie is missing, and `me.get.ts` answers `{ customer: null }` when Medusa refuses the token (a `401`, not reported). Login and register set the cookie as soon as Medusa returns the token, before the second call, with h3's defaults (`Path=/`, a session cookie, no `HttpOnly`/`Secure`/`SameSite`); logout only deletes it. `tests/unit/server/customers-routes.test.ts` pins this contract (statuses, bodies, exact `Set-Cookie`, SDK calls) through a real h3 app; change it there first if the session behaviour is meant to change.
- **Request input is parsed with zod**: every handler passes its body (`readBody`), query (`getQuery`) and route params (`getRouterParams`) through `parseRequestInput(schema, input, part)` (`server/utils/validation.ts`) and only uses what it returns. Invalid input is a `400` (`message: 'Invalid request body'`, `data: z.flattenError(...)`), never a Medusa error or a 500. The schemas live in `app/types/<domain>.ts` next to their inferred types, never inline in a handler: a form's schema is the request schema (`buildSigninSchema(t)` in the form, `signinRequestSchema = buildSigninSchema()` with zod's English messages on the server), so there is one definition per form. Query schemas are whitelists: unknown parameters are dropped and server-controlled fields cannot be overridden. h3's `readValidatedBody`/`getValidatedQuery` aren't used: they wrap the thrown error in a second one, which buries the issues.
- **Medusa responses are not validated at runtime**, deliberately: Medusa is our own backend, its responses are typed by `@medusajs/types` pinned to the same version as the SDK, and a full schema of carts/products/customers would duplicate those types and fail on every harmless Medusa addition. A shape change shows up when the SDK/types are bumped, which is when to check it. Payload responses are validated (see Payload CMS integration), because Payload is edited by hand and its contract lives only in the `payload-backend-todo` skill. The catalog (products, categories, collections) has no server handlers: its repositories call `client.store.*` straight from the client/SSR context.

When adding a new Medusa-backed feature: put the client call in a repository, put any orchestration/business logic in a service, and expose it to components via a composable. Don't call `useMedusaClient()` or `$fetch` directly from a composable or component.

### Region/country routing

Every page lives under `app/pages/[countryCode]/...`; `app/pages/index.vue` is just a redirect target. `app/middleware/region.global.ts` runs on every navigation (on the server, and in the browser during hydration and client-side navigation) and:

- Takes the country from the `countryCode` route param when it's a known region. The URL alone decides, never the cookie, so a server-rendered page is the same for every visitor (see `routeRules` / rendering).
- Otherwise redirects (`navigateTo`, default 302) with `getCountryRedirectPath()` (`app/utils/country.ts`), to the `country_code` cookie's country if it's still a region, else `useAppConfig().defaultCountry`. The cookie only picks the target; it never decides what a URL renders. A path without a country gets the prefix (`/store?page=2` -> `/pl/store?page=2`). A first segment of exactly two ASCII letters, in any case, that is not a known region is taken for a mistyped country and is replaced, not kept as part of the path (`/xx/store?x=1#h` -> `/pl/store?x=1#h`, `/xx` -> `/pl`). A segment that is `PL` for the `pl` region keeps that country (`/PL/store` -> `/pl/store`), whatever the cookie says. Anything else is a path without a country and is prefixed, so `/xxx/store` and `/pl-PL/store` still give `/pl/xxx/store`, `/pl/pl-PL/store` (a 404). That rule is why no top-level page may have a two-letter name: `/ab` would be read as a country. The redirect target always starts with a region's exact `iso_2`, which the middleware accepts as is, so it can't loop. With no regions loaded there is no redirect.
- Calls `useCountry().setCountry(...)` to sync `useState('country')` and the i18n locale. The `country_code` cookie is only written in the browser, so SSR responses never carry `Set-Cookie`.

`useCountry()`/`useCountries()` (`app/composables/country.ts`) are the source of truth for the current region; most data-fetching composables key off `country.value.region_id`.

### Internal links

Links inside the store never hard-code the country prefix; `AppLink`/`AppLinkButton` (and, outside them, `useCountryLink()` for a `UButton :to`, or `toCountryLink()` for `navigateTo`) add it from `useCountry()`. Their `to` takes two forms (`AppLinkTarget`, `app/types/link.ts`):

- **A route with params → named route** without `countryCode`: `:to="{ name: 'countryCode-products-handle', params: { handle } }"`. `experimental.typedPages` generates the route names, so a misspelled name or a missing param is a type error, and pages read their params through `useRoute('countryCode-products-handle')`. Guard an optional param (`product.collection?.handle ? { ... } : undefined`); a named route with an empty param resolves to no link instead of throwing.
- **A static page or a CMS/fallback URL → path string** relative to the country: `to="/store"`, `:to="link.url"`. Payload hands out arbitrary URLs, and CMS-provided URLs are always `to: string`.

Type a country-relative named route with `AppRoute` from `~/types/link`: it deliberately omits the required `countryCode` param and matches the `AppLink` contract. Do not rely on the root `RouteLocationRaw` here: Nuxt 4.6.3 uses Vue Router 5.4 while the root `vue-router` is 4.5.0 through `@nuxt/ui` 3.0.0, so their generated route types are not interchangeable.

### Data-fetching conventions

- Read operations use `useLazyFetch`/`useLazyAsyncData` with explicit, colon-delimited cache keys that encode the params they depend on (e.g. `` `products:${collection_id}:${category_id}:${limit}:${offset}:${region_id}` `` , `` `product:${handle}:region:${region_id}` ``). When adding a new fetcher, follow this key convention so `refreshNuxtData`/payload lookups keep working.
- By-handle repository lookups (product, category, collection) return `null` when nothing matches; their pages call `useNotFoundWhenMissing(data, status, message)` (`app/composables/not-found.ts`) so a missing handle answers a real 404 instead of an empty page, on the server and after client-side navigation.
- `useFetchProductByHandle` (`app/composables/product.ts`) has a `default()` that scans other cached `products:*` payload entries for a matching handle to avoid a network round-trip — be aware of this when changing product list cache keys.
- Cart/order/payment/customer mutation composables all follow the same shape: `loading` ref + `data` ref + async `mutate(...)`, and call `refreshNuxtData('cart')` / `refreshNuxtData('customer')` after any mutating call (done inside the service, e.g. `cart.service.ts`, `customer.service.ts`).
- Cart identity is a `cart_id` cookie managed by `useUserCart()` (90-day maxAge), not Medusa session state. Carts are created on the first add to cart (`updateOrCreateLineItem`); `useFetchCart()` only retrieves one and returns `{ cart: null }` before that, so treat `null` as an empty cart and `undefined` as still loading.
- The wishlist (saved products, `/[countryCode]/wishlist`, the hearts) is kept **in the browser only**: `useWishlist()` (`app/composables/wishlist.ts`) holds product ids in `localStorage` (`wishlist`, parsed and validated by `parseWishlist()` in `app/utils/wishlist.ts`, newest first, at most `WISHLIST_MAX_ITEMS`) and shares them through `useState`. The server render never reads it: `entries` is empty on the server and during hydration, and `app/plugins/wishlist.client.ts` loads the stored list on `app:mounted` (and on the `storage` event of another tab). So a page that shows saved state (the product page's heart) renders the same for every visitor and stays cacheable; the wishlist page itself is not `cdnCache`, `noindex` and disallowed in `robots.txt`. `useFetchWishlistProducts()` fetches the products by id in the browser only (`server: false`, key `wishlist:<ids>:<region>:<locale>`). Nothing is stored on the backend yet; the plan and the open decisions are in #79 (backend: damiankrupa1/medusaDemo#26), every stand-in in the code is marked `TODO(#79)`.

### Error reporting

Errors are reported once, where they come from an external system, through `captureError()` (`app/utils/capture-error.ts`): `apiRepository()`'s `request()`, `stripeRepository()`, the InPost Geowidget loader, `server/repository/payload.repository.ts` (a failed Payload request, `source: 'payload'` + `cms_global`; its 502 carries the reported error as `cause`, see below), `cms.repository.ts`'s `fetchGlobal()` (Payload, only what the server can't have seen: a request that got no answer from the proxy (network, offline, abort), and with `type: 'invalid_response'` a global that doesn't match its schema, reported once per distinct failure per server instance or page load via `shouldReportOnce()` in `app/utils/report-once.ts`, because it would otherwise repeat on every render; the event lists the zod `issues` as paths, codes and messages in `extra`, never the received content), Medusa's `type: 'cart'` answer in `usePlaceOrder()`, and `defineWrappedResponseHandler()` for the server API routes. Composables and components don't log errors; they only turn them into UI state. Don't name it `reportError` — that's a browser global.

`captureError(error, context)` is the only place that talks to Sentry (`@sentry/nuxt`, which supports Nuxt >= 3.7 and so Nuxt 4.6.3; `@sentry/vue` + `@sentry/node` would mean wiring the Nitro hooks by hand). Call sites don't change when the setup does.

- **Off without a DSN.** `sentry.client.config.ts` / `sentry.server.config.ts` (project root, loaded by the `@sentry/nuxt/module` in `nuxt.config.ts`) call `Sentry.init` only when `buildSentryOptions()` (`app/utils/sentry.ts`) gets a DSN. Without one `captureError()` only logs to the console, as before, and so do local dev and tests (`tests/setup.ts` mocks `@sentry/nuxt` for the plain project; the Nuxt test configuration omits the Sentry module). With a DSN it logs to the console in development only.
- **Context becomes tags.** `source` -> `source`, `type` -> `error_type`, `code` -> `error_code`, `declineCode` -> `decline_code`, `global` -> `cms_global`; any other key goes to `extra`. Reuse these keys in new call sites. `server/utils/handler.ts` reports with `source: 'server-api'` and passes the original error as `cause`, so Sentry's Nitro hook doesn't report the rethrown H3 error again. `payloadRepository()` does the same: `captureError()` marks the error it gets as captured (`__sentry_captured__`, set by Sentry's `captureException`), and the hook skips an H3 error whose `cause` carries that mark. Without it a Payload failure is two events: the hook's (an unhandled Nitro error, no `source`/`cms_global` tags) and the client's. The cause is a plain `Error` without a `status`, so `isExpectedError()` doesn't turn a Payload 404 (a wrong URL or a missing global is ours to fix) into a breadcrumb. `fetchGlobal()` leaves a proxy answer (any HTTP status) unreported because the server did: that rule assumes the server always reports, so `enableNitroErrorHandler: false` would make those failures (and any other 5xx) invisible.
- **Expected errors don't alert.** `isExpectedError()` treats a 4xx from Medusa/h3 (except 408 and 429) and a Stripe `card_error`/`validation_error` as the shopper's to fix: they become an `info` breadcrumb on the next real event, not an event. The `@sentry/nuxt` module itself already skips Nuxt errors with a 3xx/4xx status (404 pages via `showError`) and Nitro errors below 500.
- **What the module covers by itself:** Vue/Nuxt component errors (`vue:error`, `app:error`), unhandled exceptions and rejections in the browser, and unexpected Nitro errors (SSR render errors, 5xx). Don't add a second hook for those. An error that is both passed to `captureError()` and then left uncaught can be reported twice.
- **Privacy** (shop: customers, addresses, cards). `sendDefaultPii: false`, and `scrubSentryEvent()` (`beforeSend`) drops the user, cookies (incl. `medusa_jwt`), request body and query string (the Przelewy24 return carries the PaymentIntent client secret), keeps only `user-agent`/`accept`/`accept-language`/`host` headers, masks e-mails, bearer tokens, JWTs, Stripe secrets and Medusa cart/order/customer ids in messages, URLs and breadcrumbs, and replaces the value of keys such as `email`, `phone`, `address`, `cart`, `customer`, `card`, `locker`, `token` in `extra` and breadcrumb data. SDK-generated `contexts` and stack frames are not filtered. Never put customer, cart, address or payment data in a `captureError()` context; the filter is a safety net, not a licence. Extend `SENSITIVE_KEY`/`SECRET_PATTERNS` in `app/utils/sentry.ts` (with a test) when a new kind of data appears.
- **Release/environment.** `release` is `VERCEL_GIT_COMMIT_SHA` (build time for the client, runtime for the server) and `environment` is `VERCEL_ENV`, unless the `NUXT_PUBLIC_SENTRY_*` overrides are set. Tracing is off unless `NUXT_PUBLIC_SENTRY_TRACES_SAMPLE_RATE` is set; every traced request adds function time and Sentry quota on Vercel, so start low.
- **Source maps.** With `SENTRY_AUTH_TOKEN` set at build time (`nuxt.config.ts` `sentry.sourcemaps.disable` is otherwise `true`), the module generates `hidden` maps (no `sourceMappingURL` in the bundles), uploads them for the release and deletes them from `.output` afterwards, so they are never served publicly. Not verified in CI yet; check one stack trace in Sentry after the first deploy with a token.

### Payload CMS integration

Editorial/marketing content with no commerce meaning — the header's `primaryNav`, the footer's help/world/legal links and contact/social details, and most of the home page (campaign hero, brands row, studio story, journal, and the Medusa-backed category-tiles/shop-the-look sections below), see `.claude/skills/missing-cms-content/SKILL.md` for what's left — is served by a separate Payload CMS instance via `app/repository/cms.repository.ts` → `app/composables/cms.ts`, following the same repository → composable shape as the rest of the app. Medusa remains the only source of truth for products/prices/stock/cart/orders; Payload never duplicates that data. Two sections (`CategoryTiles`, `ShopTheLook`) curate real catalog items by handle, so they go through `app/services/cms.service.ts` instead of straight from the composable to the repository — composing a Payload fetch with a Medusa category/product-by-handle lookup is exactly the "business logic between repositories" the service layer exists for (see the repository → service → composable note above). Every other CMS fetcher has no such cross-domain logic and skips the service layer, same as `category`/`collection`.

- Payload's globals are public read-only today, but Payload sends no CORS headers for the storefront, so the browser can't call it: server renders worked while every client-side navigation refetched from the browser, failed, and (via `fetchGlobal()`'s catch) made the section vanish. `cms.repository.ts`'s `fetchGlobal()` therefore calls the same-origin proxy `server/api/cms/[slug].get.ts` (slugs allow-listed by `CMS_GLOBAL_SLUGS` in `app/types/cms.ts`, `locale`/`depth` validated by `cmsGlobalQuerySchema` through `server/utils/cms.ts` (a 400 with the issues), `defineCachedEventHandler` 60s + SWR; a Payload failure is a 502 that `payloadRepository()` reports once; `fetchGlobal()` doesn't repeat it), which calls `payloadRepository(payloadUrl).fetchGlobal()` (`server/repository/payload.repository.ts`, see Server layers) with `runtimeConfig.public.payloadUrl` (env `NUXT_PUBLIC_PAYLOAD_URL`) — no admin/API key involved. The repository strips trailing slashes from that base URL and aborts an upstream request after 5 seconds; an upstream timeout or error (a Payload 404 included) remains a 502. A new Payload global must be added to `CMS_GLOBAL_SLUGS` (`fetchGlobal()` only takes a `CmsGlobalSlug`, so forgetting it is a type error). If Payload ever needs a key or a draft-preview secret, move it to a private runtimeConfig that the proxy handler passes to the repository; callers don't change.
- Every global is parsed with its zod schema in `app/types/cms.ts` (`cmsNavigationSchema`, ...; the `Cms*` types are inferred from them, so schema and type can't drift), passed to `fetchGlobal()` by its fetcher. Every field is required unless the schema says otherwise; the exceptions are explicit: an image's `alt` (`''` when missing) and the footer's `contact`/`social` (each text `null` when empty, the whole group `null` when nothing is entered). Unknown fields (Payload's ids, timestamps) are stripped. A global that doesn't match, e.g. a renamed field or an image fetched with `depth=0`, is treated like a missing one below.
- A Payload outage, an unconfigured URL or an invalid global must never break a page: `fetchGlobal()` catches and returns `null`; the failure is reported by `payloadRepository()` on the server, and by `fetchGlobal()` itself via `captureError({ source: 'payload', ... })` only when the proxy gave no answer or the global is invalid. There is deliberately **no static fallback content** (no i18n copy, no bundled images, no hard-coded handles): a component whose global is `null` renders nothing for that section (`v-if` on its root; for the footer columns and contact block, on the block itself), rather than erroring or showing stand-in content. Only fixed UI chrome that is not in the Payload contract (footer column headings, tagline, "shopping" column) stays in i18n. Don't re-add a fallback in a component; fix the content in Payload.
- Payload's image URLs may point at a bucket host (Payload's `S3_FILE_URL`) instead of the Payload origin. `nuxt.config.ts` allow-lists the Payload host plus the comma-separated hostnames in `NUXT_PUBLIC_PAYLOAD_IMAGE_HOSTS` for `@nuxt/image`; an unlisted host still renders but unoptimized.
- Cache keys follow the existing convention: `` `cms:navigation:${locale}` ``, `` `cms:footer:${locale}` ``.

### `routeRules` / rendering

`nuxt.config.ts` forces SSR (`{ ssr: true }`) for `/**/products/**`, `/**/collections/**`, `/**/categories/**`, `/**/account`, `/**/store`, `/**/cart`, `/**/checkout` — keep new commerce-critical routes consistent with this if they need SEO/SSR. Nuxt 4.6 also declares `ssr` in generated Nitro route-rule types, so the old local augmentation is no longer needed.

Catalog pages (the `/[countryCode]` home, `store`, `products/[handle]`, `categories/[handle]`, `collections/[handle]`) opt into the CDN cache with `definePageMeta({ cdnCache: true })`. `app/plugins/cdn-cache.server.ts` marks such requests and `server/plugins/cdn-cache.ts` adds `CDN-Cache-Control: max-age=60, stale-while-revalidate=300`, but only to `200` responses without `Set-Cookie`, so redirects, errors and personalised responses are never shared. A page that failed is never marked, and neither is the error page Nitro renders for it: that is a request of its own to `/__nuxt_error` for the failed URL, so it resolves the same opted-in route and reaches the render hook with status `200`; the real status (a 500, or the 404 of `useNotFoundWhenMissing`) is applied afterwards to the response that carries the page, which no hook sees. So `app/plugins/cdn-cache.server.ts` skips a render with `payload.error` or `ssrContext.error`, and `server/plugins/cdn-cache.ts` skips the `/__nuxt_error` request itself (#66). A page that opts in must render the same for every visitor on the server: no cookie reads or writes during SSR, and anything per-visitor (cart, account state) stays client-only (`<ClientOnly>`). Don't opt in cart, checkout, account or order pages.

- Don't prerender catalog pages instead: that froze product data (`_payload.json`) at build time, so catalog changes in Medusa only showed up after a storefront redeploy.
- Don't use `isr`/`swr` route rules for them either: Nitro's Vercel ISR only handles literal path prefixes (ours start with a dynamic country code) and doesn't pass the query string (`page`, `sortBy`) to the render.

### Security headers (framing)

`server/plugins/frame-ancestors.ts` sets `Content-Security-Policy: frame-ancestors 'self'` on every response, so no other site can embed the storefront, cart, checkout and account pages included (clickjacking). It restricts nothing else: `frame-ancestors` has no fallback to `default-src`, so scripts, images, Stripe and the InPost Geowidget are unaffected, and nothing in this repo frames the storefront. Stripe 3DS, BLIK and Przelewy24 work the other way round (their pages are framed by, or redirect back to, ours), which this policy doesn't limit.

- **A default set on the `request` hook, not at write time**, so it also covers API routes, errors, redirects and Nitro's static asset handler, and never touches `CDN-Cache-Control`, `Set-Cookie` or the status (the CDN cache plugin is unchanged). On Vercel the static files in `.output/public` are served by the CDN without running the function, so they don't carry it; they aren't documents and can't be framed in a way that matters.
- **A response that needs another policy replaces the header** with `setResponseHeader(event, 'content-security-policy', ...)` and then owns the whole value, `frame-ancestors` included. The draft preview (#53) will do exactly that, listing its own origin, the Payload origin and the Medusa admin origins (both are listed because the frames are nested and every ancestor is checked), for preview responses only. Don't append a second `Content-Security-Policy` to relax it: browsers enforce every policy, so the intersection with `'self'` would still block the frames. A response that sets its own policy without `frame-ancestors` loses this default, so include it.
- Nitro's own error handler replaces the header with `script-src 'none'; frame-ancestors 'none'` (and `X-Frame-Options: DENY`) on JSON error responses, which is stricter, and adds `X-Frame-Options: DENY` to rendered error pages. Nothing is duplicated, and the stricter error value is fine.
- **No `X-Frame-Options`** from us: every current browser enforces `frame-ancestors` and ignores `X-Frame-Options` when it is present, so the old header would only help ancient browsers and would be one more header the preview has to override.
- Not configured in `routeRules.headers`: Nitro's Vercel preset compiles those into Vercel's routing config (applied by the platform, not by the function), and whether a header the function sets itself can still override them there isn't verified, which the preview needs. The plugin is the same on every host and testable.

### SEO (sitemap, robots.txt, canonical/hreflang, structured data)

- **Sitemap**: `@nuxtjs/sitemap` (9.1.x, the Nuxt 4-compatible line) serves `/sitemap.xml` from a single source, `server/api/__sitemap__/urls.get.ts`: it reads the countries from the cached `/api/regions` handler and walks Medusa's product/category/collection lists (`listAllPages`, `server/utils/pagination.ts`) via `medusaRepository().listSitemapCatalog()` (`server/repository/medusa.repository.ts`), then `buildCatalogSitemapUrls()` (`app/utils/seo.ts`) emits home, store and every product/category/collection page per country. The source is a `defineCachedEventHandler` (10 min, SWR), on top of the module's own 10-minute source cache; failures aren't cached. The `pages/` scan is off (`excludeAppSources: true`). A new indexable page type must be added to `buildCatalogSitemapUrls()`.
- **robots.txt**: `server/routes/robots.txt.ts` (there is no `public/robots.txt`), rules in `server/utils/robots.ts`: disallows cart, checkout, account, wishlist and order pages for every country and points to the absolute sitemap URL. Those pages also carry `robots: noindex`.
- **Canonical + hreflang**: `useCountrySeoLinks()` (`app/composables/seo.ts`) on every indexable page (home, store, product, category, collection) adds the canonical link, one `hreflang` alternate per region country and `x-default` (= `appConfig.defaultCountry`), plus `og:url`. hreflang is `<locale>-<COUNTRY>` with the locale from `getLocaleFromCountryCode()`, the same mapping the region middleware uses for i18n (`pl-PL`, `en-DE`, …). Only `?page=N` (N > 1) is kept in those URLs; sorting and other params share the canonical. By-handle pages pass `() => !!data.value` so their 404 doesn't emit a canonical. Countries come from the `countries` payload the middleware loaded; nothing reads cookies, so CDN-cached pages stay shareable.
- **Product JSON-LD**: `useProductJsonLd()` renders `buildProductJsonLd()` (`app/utils/structured-data.ts`) as `application/ld+json`: one `Offer` per variant priced in the page's region (`calculated_amount`, currency, availability from `getVariantAvailability()` — the same helper the add-to-cart button uses). Never add facts Medusa doesn't provide (brand, ratings, condition). `nuxt-schema-org` isn't used: Nuxt 4.6 ships Unhead 3, so the former compatibility concern is gone; the hand-written Product/Offer JSON-LD keeps this narrow schema explicit without another module.
- **Not indexed**: cart, checkout, account, wishlist and order pages (`noindex` + disallowed in robots.txt) and `/search` (`noindex, follow`: thin, endless `?q=` URLs; deliberately _not_ disallowed, so crawlers see the noindex). None of them call `useCountrySeoLinks()` or appear in the sitemap.
- **`<html lang>`**: set in `app/app.vue` from the i18n locale (`pl`/`en`), which the region middleware sets from the URL's country only — identical for every visitor, updated on client-side navigation. Not via `@nuxtjs/i18n`'s `useLocaleHead()`: it needs a `language` on every locale and logs a missing-`baseUrl` warning on every render with this `no_prefix` setup.

### Directory layout

- Imports use root aliases, never relative paths: `~/` for `app/` (also from `tests/`), `~~/` for the project root (e.g. `~~/server/...`). ESLint enforces it (`no-restricted-imports` in `eslint.config.mjs`, for `app/`, `server/`, `tests/`; dynamic `import()` is not checked). Details: `.claude/skills/nuxt-vue-architecture/SKILL.md` -> `## Imports`.
- `app/pages` — file-based routes, all nested under `[countryCode]`.
- `app/components` — organized by domain (`cart`, `checkout`, `product`, `order`, `collection`, `store`, `auth`, `app`, `wishlist`), with further subfolders for compound UI (e.g. `checkout/address`, `checkout/payment`, `cart/item`).
- `app/composables` — one file per domain (`cart`, `category`, `checkout`, `cms`, `collection`, `country`, `customer`, `filters`, `order`, `payment`, `product`, `wishlist`), plus `not-found` shared by the by-handle pages and `seo` (canonical/hreflang, product JSON-LD). These call into `app/services` and/or `app/repository` rather than Medusa directly (see above).
- `app/services` — `*.service.ts` business-logic layer between composables and repositories (cart, category, cms, collection, customer, order, payment, product). See the repository → service → composable note above for which ones actually have callers.
- `app/repository` — `*.repository.ts` data-access layer; `api.repository.ts` provides the shared `useMedusaClient()` + error-handling wrapper the other repositories (product, category, collection, country, order, payment, cart, customer) build on; `stripe.repository.ts` is the Stripe.js counterpart; `cms.repository.ts` is the Payload counterpart (see Payload CMS integration above) — it calls the `server/api/cms` proxy with `$fetch`, not through `apiRepository()`, since that wrapper is Medusa-specific.
- `app/utils` — pure helpers (`price`, `product`, `address`, `country`, `link`, `payment`, `percentage-diff`, `homepage`, `seo`, `structured-data`), auto-imported by Nuxt, plus `capture-error` and `sentry` (see Error reporting). `seo.ts` is also imported by the sitemap source in `server/`, so it imports its own dependencies explicitly.
- `server/repository` — `*.repository.ts`, one per external boundary (today `payload.repository.ts`, `medusa.repository.ts` for regions and the sitemap, and `customer.repository.ts` for Medusa's customer/auth calls; see Server layers). Imported explicitly with `~~/server/repository/...`.
- `server/api` — Nitro route handlers for `customers`, `regions` and `cms`; `__sitemap__/urls` feeds `/sitemap.xml` (see SEO). Catalog repositories call Medusa directly rather than through local product/category/collection handlers.
- `sentry.client.config.ts`, `sentry.server.config.ts` — Sentry init for the `@sentry/nuxt` module; they must stay at the project root (see Error reporting).
- `server/routes/robots.txt.ts` — `/robots.txt` (see SEO).
- `server/utils/handler.ts` / `server/types/medusa-error.ts` — shared error-wrapping for API routes.
- `server/utils/validation.ts` — `parseRequestInput()`, the zod request-input parser every handler uses (see Server API routes).
- `server/utils/cms.ts` — slug/query validation for the Payload proxy (`robots.ts`, `pagination.ts` are the other pure, unit-tested helpers there).

### Test runner boundary

`@nuxt/test-utils` is used only for the Vitest Nuxt unit/integration project. The real-browser e2e suite (issue #45) runs on `@playwright/test` (pinned, like Vitest), for the Chromium/WebKit/Firefox matrix, independent traces and a `webServer` lifecycle. Don't use `@nuxt/test-utils/e2e`: `vitest.config.ts` sets `NUXT_TEST_UTILS`, which strips the Medusa module from the Nuxt config, and the CDN-cache/SSR rules only exist in a production build.

- **Layout.** Specs in `tests/e2e/specs/<area>/*.spec.ts` (never matched by Vitest), helpers as plain functions in `tests/e2e/support/` (`env.ts`, `test-data.ts`, `payload-stub.ts`, `fixtures.ts`, `network-guard.ts`, `safety.ts`), config in `playwright.config.ts`. Imports use `~~/` and `~/` like everywhere else. `waitForTimeout` is an ESLint error; wait for an assertion, a response or `expect.poll`. Selectors are roles, labels and visible text (copy from `i18n/locales/*.json` or the stub), `data-testid` only where no semantic selector is stable. Use the `gotoHydrated` fixture from `~~/tests/e2e/support/fixtures` instead of `page.goto` before interacting: it waits for `useNuxtApp().isHydrating === false`.
- **App under test.** `playwright.config.ts` runs `pnpm build && pnpm preview` as its `webServer` (so the build happens in one place, with one environment), health-checks `/robots.txt` and tests `http://127.0.0.1:3100`. `E2E_SKIP_BUILD=1` reuses `.output` for local iteration (it is then your job to know it was built with the current e2e environment), `E2E_VERBOSE=1` shows the build log, `E2E_ALL_BROWSERS=1` adds Firefox and WebKit.
- **Environment.** The suite reads only `E2E_*` variables (`E2E_MEDUSA_BACKEND_URL`, `E2E_MEDUSA_PUBLISHABLE_KEY`, `E2E_STRIPE_KEY`, `E2E_APP_PORT`, `E2E_PAYLOAD_STUB_PORT`, catalog handles in `test-data.ts`) and sets every variable the build reads (`appEnv` in `env.ts`), empty ones included, so neither a shell's `NUXT_PUBLIC_*` nor `.env` reaches the e2e build. The Medusa URL and the image host list are build-time values (see Environment), which is another reason the build lives in the `webServer`. `assertSafeE2eEnvironment()` stops the run before any build with a `pk_live_` Stripe key, a Medusa/Payload URL on a production host (`PRODUCTION_HOST_MARKERS` in `safety.ts`) or a Sentry DSN/auth token (also when only set in the calling shell). Add a new production host there. Never point the suite at production data; Vercel previews must not use the production Medusa either.
- **Backends.** Payload is always the local stub (`startPayloadStub()`, started by `globalSetup`), which serves the shapes of `tests/fixtures/cms.ts` with the handles from `test-data.ts` and, like the real Payload, **sends no CORS headers**. Medusa is the only real backend: specs that need it carry `{ tag: '@medusa' }` (Stripe: `@stripe`) and are left out through `grepInvert` while `E2E_MEDUSA_BACKEND_URL` (`E2E_STRIPE_KEY`) is unset, so `pnpm test:e2e` still passes with the backend-free specs. The Medusa for pull requests is meant to be an ephemeral instance in GitHub Actions (PostgreSQL, Redis, migrations, an e2e seed that lives in the medusaDemo repository). Payment flows use Stripe test mode and InPost's sandbox, never production keys.
- **Retries and artifacts.** Retries only on CI (1); a test that passes on retry is reported as flaky, not hidden. `trace: 'on-first-retry'`, `screenshot: 'only-on-failure'`; reports go to `playwright-report/`, artifacts to `test-results/` (both git- and Prettier-ignored).
- **The #42 regression** (`specs/home/cms-sections.spec.ts`, `@medusa`) is guarded by `trackPayloadRequests()`: the browser must never call Payload itself, only `/api/cms`. It fails when `fetchGlobal()` is changed back to call Payload directly.

`@nuxtjs/medusa` (Medusa SDK integration, `server: true`), `@nuxt/ui` (with `colorMode: false`), `@nuxt/image`, `@nuxt/eslint` (stylistic rules enabled), `@nuxtjs/sitemap` (pulls in `nuxt-site-config`; see SEO).
