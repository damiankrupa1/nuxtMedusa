# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A headless e-commerce storefront ("Fashion Store") built with Nuxt 4.6.3 against a Medusa.js commerce backend. It is based on https://github.com/OlivierBelaud/nuxt-starter-medusa. Requires a supported Nuxt Node.js version (`^22.22.3 || ^24.15.0 || >=26.0.0`) and pnpm >= 9 (pinned to 11.5.0 by `packageManager`), plus a running Medusa backend.

## Commands

```bash
pnpm install       # install deps (postinstall runs `nuxt prepare`)
pnpm dev           # start dev server
pnpm build         # production build
pnpm generate      # static generation
pnpm preview       # preview a production build
pnpm lint          # eslint .
pnpm lint:fix      # eslint . --fix
pnpm format        # prettier --write .
pnpm format:check  # prettier --check .
pnpm test          # vitest run --typecheck
pnpm test:e2e      # playwright test (builds the app, see "Test runner boundary")
```

Vitest has two projects. The plain `unit` project (`tests/unit/`) runs under jsdom without booting Nuxt; keep pure utilities, types, services and server helpers here. The `nuxt` project (`tests/nuxt/`) uses `@nuxt/test-utils`' Nuxt environment for composables, middleware and components that need auto-imports, plugins, injections or registered components. Use `mountSuspended` there instead of manually stubbing Nuxt UI or app components. `pnpm test` runs both projects; its TypeScript checker remains scoped to `tests/unit/` through `tsconfig.test-unit.json`, while `pnpm lint` checks both test trees. Run a specific test with `pnpm exec vitest run --project unit tests/unit/utils/product.test.ts` or `pnpm exec vitest run --project nuxt tests/nuxt/composables/cms.test.ts`. The Nuxt test app loads the real Nuxt UI and i18n modules, but excludes the Sentry, image and sitemap modules (the Medusa client is an app plugin, `app/plugins/medusa.ts`, and loads there too; it builds a client but sends no request). Repository/service boundaries are mocked so tests never call Medusa, Payload or Stripe; no credentials or backend are required.

The Playwright e2e suite (`tests/e2e/`, `playwright.config.ts`) is separate from both Vitest projects and from `pnpm test`; see "Test runner boundary" for how it runs. After `pnpm install` run `pnpm exec playwright install chromium` once to get the browser (CI installs it with `--with-deps`).

CI has two workflows. `.github/workflows/ci.yml` runs `pnpm test`, `pnpm lint`, `pnpm format:check` and `pnpm build` on pushes to `main` and pull requests. `.github/workflows/e2e.yml` starts a throwaway Medusa with the e2e seed (medusaDemo's `e2e-medusa` action, pinned to a commit) and runs `pnpm test:e2e` against it, `@medusa` specs included (Chromium on pull requests and `main`; Firefox and WebKit through a manual `workflow_dispatch` with `all_browsers`) on Node 22, and uploads the HTML report and the traces/screenshots for 7 days (on failure also the Medusa log). It is deliberately not a required check yet, so a slow or flaky browser run can't block a merge; make it required in the branch protection rules once it is stable.

### Environment

Copy `.env.template` to `.env` and set:

- `NUXT_PUBLIC_MEDUSA_BACKEND_URL` — Medusa backend base URL (default `http://localhost:9000`)
- `NUXT_PUBLIC_MEDUSA_PUBLISHABLE_KEY` — Medusa store publishable API key
- `NUXT_PUBLIC_STRIPE_KEY` — Stripe publishable key
- `NUXT_PUBLIC_INPOST_GEOWIDGET_TOKEN` — InPost Geowidget token for the parcel locker picker in the delivery step
- `NUXT_PUBLIC_PAYLOAD_URL` — Payload CMS base URL (editorial/marketing content; see Payload CMS integration below). All editorial content (header nav, footer links/contact, home sections and their images) comes only from Payload; there is no static fallback, so the sections that need it are not rendered while it is unset or unreachable.
- `NUXT_PUBLIC_SITE_URL` — public origin of the storefront (e.g. `https://shop.example.com`), read by `nuxt-site-config` (installed by `@nuxtjs/sitemap`) for canonical/hreflang links, `sitemap.xml` and `robots.txt`. Optional — falls back to the request origin, so set it in production to keep preview/alias hosts out of canonical URLs.
- `NUXT_PUBLIC_SENTRY_DSN` — Sentry DSN (public by design; see Error reporting). Optional: empty means Sentry is off and errors only go to the console. Use the same Sentry organization as the Medusa backend and admin (damiankrupa1/medusaDemo#18), as its own project. Related, all optional: `SENTRY_DSN` (server-only DSN, defaults to the public one), `NUXT_PUBLIC_SENTRY_ENVIRONMENT` (defaults to Vercel's `VERCEL_ENV`, then `NODE_ENV`), `NUXT_PUBLIC_SENTRY_RELEASE` (defaults to `VERCEL_GIT_COMMIT_SHA`), `NUXT_PUBLIC_SENTRY_TRACES_SAMPLE_RATE` (0-1; empty keeps tracing off).
- `NUXT_PAYLOAD_PREVIEW_SECRET`, `NUXT_PAYLOAD_PREVIEW_API_KEY`, `NUXT_PAYLOAD_PREVIEW_API_KEY_COLLECTION` (default `service-users`), `NUXT_PAYLOAD_PREVIEW_FRAME_ANCESTORS` — the draft preview (see "Draft preview" below). Private runtime config, read at runtime (nothing is baked into the build), never `NUXT_PUBLIC_*`. Optional: without the secret (at least 32 characters, the same value as `PREVIEW_SECRET` in Payload) or the API key every `/api/preview` route answers 404.
- `SENTRY_ORG`, `SENTRY_PROJECT`, `SENTRY_AUTH_TOKEN` — build-time only, for the source map upload. Keep them in Vercel/CI secrets, never as `NUXT_PUBLIC_*`. Without `SENTRY_AUTH_TOKEN` no source maps are generated or uploaded.

Several of these are read by `nuxt.config.ts` when the app is **built**, not when it starts, so changing them needs a new build: the `@nuxt/image` host allow-list (`NUXT_PUBLIC_PAYLOAD_URL` + `NUXT_PUBLIC_PAYLOAD_IMAGE_HOSTS`) and the Sentry release and source map settings. The `runtimeConfig.public.*` values (`medusa.backendUrl`/`publishableKey`, `stripeKey`, `payloadUrl`, Sentry DSN) are baked in as defaults and can still be overridden by the same variable at runtime. A `.env` file only fills variables that are undefined, so a variable set to an empty string in the environment wins over it. The e2e suite relies on that (see "Test runner boundary").

### Git hooks (husky)

- `pre-commit` runs `pnpm lint` (`eslint .` on the whole project, not only staged files) and blocks the commit on failure. That is all it does: `package.json` has a `lint-staged` config (`eslint --fix` + `prettier --write` on `*.{js,ts,vue}`, `prettier --write` on `*.{json,css,scss,md}`), but no hook calls it, so nothing formats or auto-fixes staged files. Run `pnpm format:check` / `prettier --write <files>` yourself.
- `commit-msg` runs commitlint (`@commitlint/config-conventional` + `commitlint.config.js`). Commit subjects must use `type: description` with `type` restricted to `feat|fix|refactor|docs|style|test|build`, a non-empty subject, max 72 chars. The hook prints commitlint's errors but does not block the commit (the script ends without `exit 1`, so it always exits 0), so check its output yourself.

## Architecture

### Three-layer data access: repository → service → composable

Most Medusa Store API access flows through three layers under `app/`:

1. **Repository** (`app/repository/*.repository.ts`): thin data-access functions. `apiRepository()` wraps `useMedusaClient()` (`app/composables/medusa.ts`, the client `app/plugins/medusa.ts` provides) with a `request()` helper that reports (`captureError`) and rethrows errors; the `product`, `category`, `collection`, `order`, `payment`, and `cart` repositories all call `apiRepository()` and issue `client.store.*` calls directly. `customer.repository.ts` and `country.repository.ts` are the exceptions: they call `server/api/customers/**` and `server/api/regions` via `$fetch` (customers through `apiRepository()`'s `request()`; regions report only a request without an answer, since the server reported every answer, as `fetchGlobal()` does), because auth needs the server-side cookie session and regions are cached on the server. `stripe.repository.ts` wraps Stripe.js instead of Medusa (lazy `loadStripe`, card element, card/BLIK/Przelewy24 confirmations, PaymentIntent lookup) and turns Stripe's `{ error }` results into thrown errors, reporting all but the customer-side ones (`card_error`, `validation_error`).
2. **Service** (`app/services/*.service.ts`): composes repository calls and adds business logic. `cart.service.ts`, `customer.service.ts` and `payment.service.ts` carry real logic (cart-id lifecycle, region reconciliation, `refreshNuxtData` side effects; for payment, picking the Stripe confirmation by provider and checking the payment Przelewy24 redirected back from) and are consumed by composables. `category.service.ts`, `collection.service.ts`, `order.service.ts`, and `product.service.ts` are currently thin pass-throughs with **no callers** — the composables for those domains call the repository directly instead. If you touch one of those domains, either wire the composable through its service (so the layer earns its keep) or remove the unused service — don't add a fourth pattern (this is about `app/`; the server side has its own layers, below).
3. **Composable** (`app/composables/*.ts`): the Vue-facing layer. Wraps repository/service calls in `useLazyAsyncData`/`useLazyFetch` for reads (see cache-key convention below), or a `loading`/`data`/`mutate()` shape for writes.

**Server API routes** (`server/api/**`): Nitro/H3 handlers; `customers/**` build their `customerRepository(serverMedusaClient(event))` from `serverMedusaClient(event)` (`server/utils/medusa.ts`) and are wrapped in `defineWrappedResponseHandler` (`server/utils/handler.ts`), which catches thrown errors, extracts `MedusaError` `status`/`message`, and re-throws as an H3 error (an error that already is an H3 error, like a validation 400, passes through unchanged). Only `server/api/customers/**` (login/register/logout/me, for the server-side cookie session), `server/api/regions` (a `defineCachedEventHandler`, since the region middleware needs regions on every server render) and `server/api/cms/[slug]` (the Payload proxy, see Payload CMS integration; not Medusa, so it is not wrapped in `defineWrappedResponseHandler`) are called from `app/` today.

**Server layers** (`server/`): the same idea applies on the server, so a handler never talks to an external system itself.

- `server/repository/*.repository.ts`: one file per external boundary (Medusa, Payload). It alone knows that system's URL or SDK calls, normalises its input (e.g. trailing slashes), sets the timeout and maps an upstream failure to an H3 error. It reports an external system's failure itself, through `captureError()` like `apiRepository()` does (the Payload repository does it with `source: 'payload'` and the slug as `global`), and links the reported error as the `cause` of the H3 error it throws, so Sentry's Nitro hook doesn't report that H3 error again; the handler and the app side don't repeat it. It takes its configuration as arguments (`payloadRepository(baseUrl)`), so a test needs no runtime config. Nitro auto-imports only `server/utils`, so a handler imports it explicitly: `~~/server/repository/payload.repository`.
- `server/repository/customer.repository.ts` (Medusa auth + store customer, for `customers/**`) differs from the Payload one in two ways. It takes the request's SDK client, `customerRepository(serverMedusaClient(event))`, never a client shared at module level, and every call made as the customer takes the token as an argument. And it neither catches nor reports Medusa errors: its only callers are wrapped in `defineWrappedResponseHandler()`, which already reports a Medusa error once (`source: 'server-api'`) and keeps its status and message, so reporting in the repository would double it.
  - Login and register use the SDK's `auth.login()`/`auth.register()` (`customer`/`emailpass`); a login answer that is not a token (redirect, MFA challenge, verification step) is a 500. That is safe only with the server client: `serverMedusaClient(event)` (`server/utils/medusa.ts`, typed, one client per request on `event.context`) has `auth: { type: 'jwt', jwtTokenStorageMethod: 'nostore' }` (#89). With the page client's `type: 'session'`, `auth.login()` follows the token with `POST /auth/session`, a Medusa cookie session (`connect.sid`, kept in the backend's session store) that the server never uses and nothing ends (#82); with `'local'` storage `auth.register()` stores the token in `localStorage` without awaiting it, an unhandled rejection on the server. Never build the server client from the page client's config. `tests/unit/server/customer.repository.test.ts` and `medusa-client.test.ts` run login and register against the installed js-sdk with that config and a stubbed network (one request each, no `/auth/session`, no unhandled rejection). The registration token has an empty `actor_id`, which Medusa refuses for `/store/customers/me`, so register exchanges it with `refreshToken()` (the SDK's `auth.refresh()`, `POST /auth/token/refresh`) once the customer exists, and that token is the session (#45 found it: with the registration token a new customer was signed out on the next request).
- `server/services/*.service.ts`: only when something composes several repository calls with logic. No pass-through services. None exists yet: login and register were the expected case, but they only hand the token from one Medusa call to the next and set or clear the cookie after the last, which is HTTP, so they stay repository calls in the handler.
- Handlers (`server/api/**`) do HTTP only: `parseRequestInput`, cookies, status codes, cache options, then one repository or service call (login: two, register: three, with the session cookie set or cleared after the last).
- Every server handler follows this since issue #43 (the Payload proxy, `regions`, `__sitemap__/urls` and `customers/**`). Don't write new handlers the old way.
- `medusaRepository(event)` (`server/repository/medusa.repository.ts`) wraps `serverMedusaClient(event)` for `regions` (`listRegions()`) and the sitemap (`listSitemapCatalog()`, which walks products, categories and collections with `listAllPages`). It reports a Medusa failure once (`source: 'medusa'`; a 4xx stays a breadcrumb) and throws an H3 error with Medusa's status (500 without one) and the reported error as `cause`. Handlers that use it are therefore not wrapped in `defineWrappedResponseHandler`, which would report the same failure again. `customers/**` is wrapped on purpose, because `customerRepository()` does not report (see above).

- **The customer session** is the JWT Medusa issues at login/register, kept in the `medusa_jwt` cookie and handled only by `server/utils/session-cookie.ts` (`getSessionToken`, `setSessionCookie`, `clearSessionCookie`; issue #78). Authenticated handlers (`me.get.ts`, `me.post.ts`) pass the token to `customerRepository()`, which sends it as `Authorization: Bearer <token>`.
  - **Attributes:** `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age` until the token's `exp` (decoded, not verified, since Medusa verifies it; 24h, Medusa's default `jwtExpiresIn`, when unreadable), and `Secure` when the request came over https, i.e. h3's `getRequestProtocol()`, which trusts `x-forwarded-proto: https` (Vercel's edge sets it). Local `pnpm dev`/`pnpm preview` and the e2e build run on plain http and get no `Secure`. A deployment behind a TLS proxy that doesn't send `x-forwarded-proto` would lose `Secure`. Clearing uses the same attributes, so it replaces the cookie it deletes.
  - **Nothing in the browser may read it.** The browser's Medusa client (`useMedusaClient()`, `auth.type: 'session'`, kept from the former `@nuxtjs/medusa` defaults by `buildBrowserMedusaConfig()` in `app/utils/medusa.ts`) never authenticates as the customer, and every customer call goes through `server/api/customers/**` (`app/repository/customer.repository.ts`). Customer data that the browser needs comes from `/api/customers/me`; don't read the token with JS or move a customer call to the browser client.
  - **The server render sees the session too** (#81). During SSR the global `$fetch` sends none of the visitor's cookies, so `customerRepository().fetchCustomer()` (`app/repository/customer.repository.ts`) asks `me` through `useRequestFetch()`, which forwards the page request's headers (and is `$fetch` itself in the browser). `useFetchCustomer()` (key `customer`) therefore fetches the customer in the server render of per-visitor pages (account, wishlist's guest banner), and a signed-in customer's reload shows the account, not the sign-in form. On a `cdnCache` page it passes `server: false` and fetches in the browser only, because such a page must render the same for every visitor (see `routeRules` / rendering). Take `useRequestFetch()` when the repository is created (in setup), not inside the async handler. `tests/e2e/specs/account/session.spec.ts` (`@medusa`) checks the server-rendered account page with JavaScript off.
  - **Login and register** set the cookie only after every Medusa call succeeded. When a later call (`retrieveCustomer`; `createCustomer` or `refreshToken`) fails, they clear it, which also drops a session the browser had before, and Medusa's status and message go on unchanged, reported once by the wrapper. A failed first call (wrong password, existing identity) and a `400` leave the cookie alone (no `Set-Cookie`). After a failed `createCustomer` Medusa keeps the auth identity without a customer, so registering that email again answers "Identity with email already exists".
  - **`GET me`** answers `{ customer: null }` without a (non-empty) cookie, without asking Medusa, and also when Medusa refuses the token (a `401`, not reported; the cookie isn't cleared then, it expires with the token). **`POST me`** answers `401` before reading the body or touching Medusa when the cookie is missing or empty.
  - **Logout** clears the cookie and does not call Medusa. Known limitation: Medusa's customer JWT is stateless and can't be revoked (Medusa 2.19 has no revocation route; the SDK's `auth.logout()` only ends a Medusa cookie session via `DELETE /auth/session`, which this server never opens since #82), so a token copied before logout stays valid until its `exp`, 24h at most with today's backend config. Shortening that means setting `http.jwtExpiresIn` in the Medusa backend; the cookie follows the token's `exp` by itself.
  - `tests/unit/server/customers-routes.test.ts` pins this contract (statuses, bodies, exact `Set-Cookie` over http and https, SDK calls, Sentry events) through a real h3 app; change it there first if the session behaviour is meant to change. `tests/unit/server/session-cookie.test.ts` covers the lifetime read from the token.
- **Request input is parsed with zod**: every handler passes its body (`readBody`), query (`getQuery`) and route params (`getRouterParams`) through `parseRequestInput(schema, input, part)` (`server/utils/validation.ts`) and only uses what it returns. Invalid input is a `400` (`message: 'Invalid request body'`, `data: z.flattenError(...)`), never a Medusa error or a 500. The schemas live in `app/types/<domain>.ts` next to their inferred types, never inline in a handler: a form's schema is the request schema (`buildSigninSchema(t)` in the form, `signinRequestSchema = buildSigninSchema()` with zod's English messages on the server), so there is one definition per form. Query schemas are whitelists: unknown parameters are dropped and server-controlled fields cannot be overridden. h3's `readValidatedBody`/`getValidatedQuery` aren't used: they wrap the thrown error in a second one, which buries the issues.
- **Medusa responses are validated with narrow zod schemas** (#84; until then they deliberately weren't). The backend is deployed on its own, so a version drift or a changed field showed up as `undefined` far from its cause; a full schema of carts/products/customers would still duplicate `@medusajs/types` and fail on every harmless Medusa addition. So a schema lists **only the fields the code reads**, as `z.looseObject`s, and lives in `app/types/<domain>.ts`; each object is written `z.looseObject({ ... } satisfies MedusaResponseShape<SdkType>)` (`app/types/medusa.ts`), so it can't name a field the SDK type lacks or widen one. One helper, `parseMedusaResponse(schema, data, label, policy)` (`app/utils/medusa-response.ts`), holds the policy and returns `data` itself: `hard` (session, payments) throws `Unexpected <label> response from Medusa` (the zod error as `cause`, no received values) for the caller's error path to report; `soft` (displayed or routed-on data) reports once and returns `{ success: false, error }` for the existing error state (see Error reporting). Validated today: the session and customer answers in `server/repository/customer.repository.ts` (hard: tokens, refresh, `customer.id`/email/names/phone; a mismatch is a 500 and no session cookie) and the regions in `medusaRepository().listRegions()` (soft: a mismatch is a 502 like a regions outage, never an empty list the cache would keep). Payments, the cart and the catalog are not validated yet (rest of #84). Recorded samples are in `tests/fixtures/medusa.ts`; `tests/e2e/specs/contract/medusa-responses.spec.ts` (`@medusa`) checks the real Medusa against the schemas. Payload responses are validated too (see Payload CMS integration). The catalog (products, categories, collections) has no server handlers: its repositories call `client.store.*` straight from the client/SSR context.

When adding a new Medusa-backed feature: put the client call in a repository, put any orchestration/business logic in a service, and expose it to components via a composable. Don't call `useMedusaClient()` or `$fetch` directly from a composable or component.

### Region/country routing

Every page lives under `app/pages/[countryCode]/...`; `app/pages/index.vue` is just a redirect target. `app/middleware/region.global.ts` runs on every navigation (on the server, and in the browser during hydration and client-side navigation) and:

- Takes the country from the `countryCode` route param when it's a known region. The URL alone decides, never the cookie, so a server-rendered page is the same for every visitor (see `routeRules` / rendering).
- Otherwise redirects (`navigateTo`, default 302) with `getCountryRedirectPath()` (`app/utils/country.ts`), to the `country_code` cookie's country if it's still a region, else `useAppConfig().defaultCountry`. The cookie only picks the target; it never decides what a URL renders. A path without a country gets the prefix (`/store?page=2` -> `/pl/store?page=2`). A first segment of exactly two ASCII letters, in any case, that is not a known region is taken for a mistyped country and is replaced, not kept as part of the path (`/xx/store?x=1#h` -> `/pl/store?x=1#h`, `/xx` -> `/pl`). A segment that is `PL` for the `pl` region keeps that country (`/PL/store` -> `/pl/store`), whatever the cookie says. Anything else is a path without a country and is prefixed, so `/xxx/store` and `/pl-PL/store` still give `/pl/xxx/store`, `/pl/pl-PL/store` (a 404). That rule is why no top-level page may have a two-letter name: `/ab` would be read as a country. The redirect target always starts with a region's exact `iso_2`, which the middleware accepts as is, so it can't loop. With no regions loaded there is no redirect.
- Calls `useCountry().setCountry(...)` to sync `useState('country')` and the i18n locale. The `country_code` cookie is only written in the browser, so SSR responses never carry `Set-Cookie`.

`useCountry()`/`useCountries()` (`app/composables/country.ts`) are the source of truth for the current region; most data-fetching composables key off `country.value.region_id`.

### Internal links

Links inside the store never hard-code the country prefix; `AppLink`/`AppLinkButton` (and, outside them, `useCountryLink()` for a `UButton :to`, or `toCountryLink()` for `navigateTo`) add it from `useCountry()`. Their `to` takes two forms (`AppLinkTarget`, `app/types/link.ts`):

- **A route with params → named route** without `countryCode`: `:to="{ name: 'countryCode-products-handle', params: { handle } }"`. `experimental.typedPages` generates the route names, so a misspelled name or a missing param is a type error, and pages read their params through `useRoute('countryCode-products-handle')`. Guard an optional param (`product.collection?.handle ? { ... } : undefined`); a named route with an empty param resolves to no link instead of throwing.
- **A static page or a CMS/fallback URL → path string** relative to the country: `to="/store"`, `:to="link.url"`. Payload hands out arbitrary URLs, and CMS-provided URLs are always `to: string`.

Type a country-relative named route with `AppRoute` from `~/types/link`: it deliberately omits the required `countryCode` param and matches the `AppLink` contract. Do not rely on the root `RouteLocationRaw` here: Nuxt 4.6.3 uses Vue Router 5.4 while the root `vue-router` is 4.5.0 through `@nuxt/ui` 3.0.0, so their generated route types are not interchangeable.

### Data-fetching conventions

- Read operations use `useLazyFetch`/`useLazyAsyncData` with explicit, colon-delimited cache keys that encode the params they depend on (e.g. `` `products:${collection_id}:${category_id}:${limit}:${offset}:${region_id}` `` , `` `product:${handle}:region:${region_id}` ``). When adding a new fetcher, follow this key convention so `refreshNuxtData`/payload lookups keep working.
- A Medusa answer the code relies on is checked where it enters, in the repository, with `parseMedusaResponse()` (see Server API routes), never in a composable or component. Pick the policy by what a wrong answer costs: `hard` where going on would be wrong (session, payments, order), `soft` where the page has an error state for it already (regions today; later the catalog). A new schema gets the four tests of `tests/unit/types/country.test.ts`: the recorded sample, an added field (passes), a missing used field, a wrong type.
- By-handle repository lookups (product, category, collection) return `null` when nothing matches; their pages call `useNotFoundWhenMissing(data, status, message)` (`app/composables/not-found.ts`) so a missing handle answers a real 404 instead of an empty page, on the server and after client-side navigation.
- `useFetchProductByHandle` (`app/composables/product.ts`) has a `default()` that scans other cached `products:*` payload entries for a matching handle to avoid a network round-trip — be aware of this when changing product list cache keys.
- Cart/order/payment/customer mutation composables all follow the same shape: `loading` ref + `data` ref + async `mutate(...)`, and call `refreshNuxtData('cart')` / `refreshNuxtData('customer')` after any mutating call (done inside the service, e.g. `cart.service.ts`, `customer.service.ts`).
- Cart identity is a `cart_id` cookie managed by `useUserCart()` (90-day maxAge), not Medusa session state. Carts are created on the first add to cart (`updateOrCreateLineItem`); `useFetchCart()` only retrieves one and returns `{ cart: null }` before that, so treat `null` as an empty cart and `undefined` as still loading.
- The wishlist (saved products, `/[countryCode]/wishlist`, the hearts) is kept **in the browser only**: `useWishlist()` (`app/composables/wishlist.ts`) holds product ids in `localStorage` (`wishlist`, parsed and validated by `parseWishlist()` in `app/utils/wishlist.ts`, newest first, at most `WISHLIST_MAX_ITEMS`) and shares them through `useState`. The server render never reads it: `entries` is empty on the server and during hydration, and `app/plugins/wishlist.client.ts` loads the stored list on `app:mounted` (and on the `storage` event of another tab). So a page that shows saved state (the product page's heart) renders the same for every visitor and stays cacheable; the wishlist page itself is not `cdnCache`, `noindex` and disallowed in `robots.txt`. `useFetchWishlistProducts()` fetches the products by id in the browser only (`server: false`, key `wishlist:<ids>:<region>:<locale>`). Nothing is stored on the backend yet; the plan and the open decisions are in #79 (backend: damiankrupa1/medusaDemo#26), every stand-in in the code is marked `TODO(#79)`.

### Error reporting

Errors are reported once, where they come from an external system, through `captureError()` (`app/utils/capture-error.ts`): `apiRepository()`'s `request()`, `stripeRepository()`, the InPost Geowidget loader, `server/repository/payload.repository.ts` (a failed Payload request, `source: 'payload'` + `cms_global`; its 502 carries the reported error as `cause`, see below), `cms.repository.ts`'s `fetchGlobal()` (Payload, only what the server can't have seen: a request that got no answer from the proxy (network, offline, abort), and with `type: 'invalid_response'` a global that doesn't match its schema, reported once per distinct failure per server instance or page load via `shouldReportOnce()` in `app/utils/report-once.ts`, because it would otherwise repeat on every render; the event lists the zod `issues` as paths, codes and messages in `extra`, never the received content), Medusa's `type: 'cart'` answer in `usePlaceOrder()`, `parseMedusaResponse()`'s soft path (a Medusa answer that doesn't match its schema, `source: 'medusa'`, `type: 'invalid_response'`, `response: <label>` and the issues in `extra`, once per distinct failure via `shouldReportOnce()`, like Payload; its hard path reports nothing itself, the handler wrapper or `request()` reports the thrown error once), the draft preview's session check and draft requests that got no answer (as a new error without the token, see "Draft preview"), and `defineWrappedResponseHandler()` for the server API routes. Composables and components don't log errors; they only turn them into UI state. Don't name it `reportError` — that's a browser global.

`captureError(error, context)` is the only place that talks to Sentry (`@sentry/nuxt`, which supports Nuxt >= 3.7 and so Nuxt 4.6.3; `@sentry/vue` + `@sentry/node` would mean wiring the Nitro hooks by hand). Call sites don't change when the setup does.

- **Off without a DSN.** `sentry.client.config.ts` / `sentry.server.config.ts` (project root, loaded by the `@sentry/nuxt/module` in `nuxt.config.ts`) call `Sentry.init` only when `buildSentryOptions()` (`app/utils/sentry.ts`) gets a DSN. Without one `captureError()` only logs to the console, as before, and so do local dev and tests (`tests/setup.ts` mocks `@sentry/nuxt` for the plain project; the Nuxt test configuration omits the Sentry module). With a DSN it logs to the console in development only.
- **Context becomes tags.** `source` -> `source`, `type` -> `error_type`, `code` -> `error_code`, `declineCode` -> `decline_code`, `global` -> `cms_global`; any other key goes to `extra`. Reuse these keys in new call sites. `server/utils/handler.ts` reports with `source: 'server-api'` and passes the original error as `cause`, so Sentry's Nitro hook doesn't report the rethrown H3 error again. `payloadRepository()` does the same: `captureError()` marks the error it gets as captured (`__sentry_captured__`, set by Sentry's `captureException`), and the hook skips an H3 error whose `cause` carries that mark. Without it a Payload failure is two events: the hook's (an unhandled Nitro error, no `source`/`cms_global` tags) and the client's. The regions' 502 for an invalid answer relies on the same mark: `parseMedusaResponse()` hands out the same reported error for every repeat, so a repeat is skipped by the hook as well. The cause is a plain `Error` without a `status`, so `isExpectedError()` doesn't turn a Payload 404 (a wrong URL or a missing global is ours to fix) into a breadcrumb. `fetchGlobal()` leaves a proxy answer (any HTTP status) unreported because the server did: that rule assumes the server always reports, so `enableNitroErrorHandler: false` would make those failures (and any other 5xx) invisible.
- **Expected errors don't alert.** `isExpectedError()` treats a 4xx from Medusa/h3 (except 408 and 429) and a Stripe `card_error`/`validation_error` as the shopper's to fix: they become an `info` breadcrumb on the next real event, not an event. The `@sentry/nuxt` module itself already skips Nuxt errors with a 3xx/4xx status (404 pages via `showError`) and Nitro errors below 500.
- **What the module covers by itself:** Vue/Nuxt component errors (`vue:error`, `app:error`), unhandled exceptions and rejections in the browser, and unexpected Nitro errors (SSR render errors, 5xx). Don't add a second hook for those. An error that is both passed to `captureError()` and then left uncaught can be reported twice.
- **Privacy** (shop: customers, addresses, cards). `sendDefaultPii: false`, and `scrubSentryEvent()` (`beforeSend`) drops the user, cookies (incl. `medusa_jwt`), request body and query string (the Przelewy24 return carries the PaymentIntent client secret), keeps only `user-agent`/`accept`/`accept-language`/`host` headers, masks e-mails, bearer tokens, JWTs, Stripe secrets and Medusa cart/order/customer ids in messages, URLs and breadcrumbs, and replaces the value of keys such as `email`, `phone`, `address`, `cart`, `customer`, `card`, `locker`, `token` in `extra` and breadcrumb data. SDK-generated `contexts` and stack frames are not filtered. Never put customer, cart, address or payment data in a `captureError()` context; the filter is a safety net, not a licence. Extend `SENSITIVE_KEY`/`SECRET_PATTERNS` in `app/utils/sentry.ts` (with a test) when a new kind of data appears.
- **Release/environment.** `release` is `VERCEL_GIT_COMMIT_SHA` (build time for the client, runtime for the server) and `environment` is `VERCEL_ENV`, unless the `NUXT_PUBLIC_SENTRY_*` overrides are set. Tracing is off unless `NUXT_PUBLIC_SENTRY_TRACES_SAMPLE_RATE` is set; every traced request adds function time and Sentry quota on Vercel, so start low.
- **Source maps.** With `SENTRY_AUTH_TOKEN` set at build time (`nuxt.config.ts` `sentry.sourcemaps.disable` is otherwise `true`), the module generates `hidden` maps (no `sourceMappingURL` in the bundles), uploads them for the release and deletes them from `.output` afterwards, so they are never served publicly. Not verified in CI yet; check one stack trace in Sentry after the first deploy with a token.

### Payload CMS integration

Editorial/marketing content with no commerce meaning — the header's `primaryNav`, the footer's help/world/legal links and contact/social details, and most of the home page (campaign hero, brands row, studio story, journal, and the Medusa-backed category-tiles/shop-the-look sections below), see `.claude/skills/missing-cms-content/SKILL.md` for what's left — is served by a separate Payload CMS instance via `app/repository/cms.repository.ts` → `app/composables/cms.ts`, following the same repository → composable shape as the rest of the app. Medusa remains the only source of truth for products/prices/stock/cart/orders; Payload never duplicates that data. Two sections (`CategoryTiles`, `ShopTheLook`) curate real catalog items by handle, so they go through `app/services/cms.service.ts` instead of straight from the composable to the repository — composing a Payload fetch with a Medusa category/product-by-handle lookup is exactly the "business logic between repositories" the service layer exists for (see the repository → service → composable note above). Every other CMS fetcher has no such cross-domain logic and skips the service layer, same as `category`/`collection`.

- Payload's globals are public read-only today, but Payload sends no CORS headers for the storefront, so the browser can't call it: server renders worked while every client-side navigation refetched from the browser, failed, and (via `fetchGlobal()`'s catch) made the section vanish. `cms.repository.ts`'s `fetchGlobal()` therefore calls the same-origin proxy `server/api/cms/[slug].get.ts` (slugs allow-listed by `CMS_GLOBAL_SLUGS` in `app/types/cms.ts`, `locale`/`depth` validated by `cmsGlobalQuerySchema` through `server/utils/cms.ts` (a 400 with the issues), `defineCachedEventHandler` 60s + SWR; a Payload failure is a 502 that `payloadRepository()` reports once; `fetchGlobal()` doesn't repeat it), which calls `payloadRepository(payloadUrl).fetchGlobal()` (`server/repository/payload.repository.ts`, see Server layers) with `runtimeConfig.public.payloadUrl` (env `NUXT_PUBLIC_PAYLOAD_URL`) — no admin/API key involved (the draft preview's key is used only by `payloadDraftRepository()`, see "Draft preview"). The repository strips trailing slashes from that base URL and aborts an upstream request after 5 seconds; an upstream timeout or error (a Payload 404 included) remains a 502. A new Payload global must be added to `CMS_GLOBAL_SLUGS` (`fetchGlobal()` only takes a `CmsGlobalSlug`, so forgetting it is a type error). The public proxy never sends credentials or `draft`: `payloadRepository().fetchGlobal()` builds its query from `locale` and `depth` only.
- Every global is parsed with its zod schema in `app/types/cms.ts` (`cmsNavigationSchema`, ...; the `Cms*` types are inferred from them, so schema and type can't drift), passed to `fetchGlobal()` by its fetcher. Every field is required unless the schema says otherwise; the exceptions are explicit: an image's `alt` (`''` when missing) and the footer's `contact`/`social` (each text `null` when empty, the whole group `null` when nothing is entered). Unknown fields (Payload's ids, timestamps) are stripped. A global that doesn't match, e.g. a renamed field or an image fetched with `depth=0`, is treated like a missing one below.
- A Payload outage, an unconfigured URL or an invalid global must never break a page: `fetchGlobal()` catches and returns `null`; the failure is reported by `payloadRepository()` on the server, and by `fetchGlobal()` itself via `captureError({ source: 'payload', ... })` only when the proxy gave no answer or the global is invalid. There is deliberately **no static fallback content** (no i18n copy, no bundled images, no hard-coded handles): a component whose global is `null` renders nothing for that section (`v-if` on its root; for the footer columns and contact block, on the block itself), rather than erroring or showing stand-in content. Only fixed UI chrome that is not in the Payload contract (footer column headings, tagline, "shopping" column) stays in i18n. Don't re-add a fallback in a component; fix the content in Payload.
- Payload's image URLs may point at a bucket host (Payload's `S3_FILE_URL`) instead of the Payload origin. `nuxt.config.ts` allow-lists the Payload host plus the comma-separated hostnames in `NUXT_PUBLIC_PAYLOAD_IMAGE_HOSTS` for `@nuxt/image`; an unlisted host still renders but unoptimized.
- Cache keys follow the existing convention: `` `cms:navigation:${locale}` ``, `` `cms:footer:${locale}` ``. In the draft preview every one of them gets `:preview` appended (`toCmsCacheKey()`, see "Draft preview"); a new CMS composable must go through `useCmsAsyncData()` in `app/composables/cms.ts` to get that.

### Draft preview (#53)

Editors see unpublished Payload drafts on the real storefront from Payload's Preview button and Live Preview pane (Payload side: simple-landing-page-nuxt#20, PRs #26/#30; contract in the `payload-backend-todo` skill). The server side (1-6 below) and the page side ("In the browser" below) are both in place. A preview page is first rendered with the published content and switches to the drafts once the app has hydrated.

**The rule: the server never renders a draft and never stores one in any cache.** Drafts are fetched only by the browser, from `/api/preview/cms/<slug>`, which is not cached. A page request with `?preview` is an ordinary render of the published content that is kept out of the CDN. Each layer below holds on its own:

1. **Entry** `GET /api/preview?token=<JWT>&locale=<en|pl>&path=/&global=<slug>` (`server/api/preview/index.get.ts`, the link Payload builds): parses the query (`previewEntryQuerySchema` in `app/types/preview.ts`, 400), verifies the token and that its `locale`/`global` claims match the query (401 with a plain-text reason, readable in Payload's frame; never a fallback to anything), maps the locale to a country (`pl` -> `pl`, `en` -> the first other region country by name, else `appConfig.defaultCountry`) and answers `302` to `/{cc}{path}?preview=1#token=<JWT>`. The token moves to the fragment, so the page request and everything after it carry no token; only this first request has it in its query string, because that is how Payload builds the link (so it reaches access logs; Sentry drops query strings and masks JWTs).
2. **Token** (`verifyPreviewToken()`, `server/utils/preview-token.ts`, `jose`): HS256 only (`none`, RS256, HS512 refused), `iss: payload-cms`, `aud: storefront-preview`, `sub`, `iat`, `exp` required, ±60 s clock tolerance, lifetime (`exp - iat`) at most 2 h (Payload issues exactly 2 h, quantised to the hour), no `iat` in the future, secret of at least 32 characters. After the entry, the browser sends it only in the `x-preview-token` header, never in a query.
3. **`POST /api/preview/session`** answers `{ expiresAt }` for a valid token, else 401. **`GET /api/preview/cms/<slug>`** checks the token first (401), then the `CMS_GLOBAL_SLUGS` allow-list (404), the Payload URL (503) and `locale`/`depth` (400), then calls `payloadDraftRepository().fetchDraftGlobal()` (`draft=true`, `Authorization: <collection> API-Key <key>`, same timeout and 502 mapping as the public call). Both are plain `defineEventHandler`s: never wrap a preview route in `defineCachedEventHandler` (`preview-cms-route.test.ts` and `preview-leak.test.ts` fail if you do).
4. **The public proxy can't ask for a draft**: `server/api/cms/[slug]` parses a whitelist without `draft`, `payloadRepository().fetchGlobal()` sends no credentials, and Nitro's cached handler hands no request headers to it (no `varies`). Only the preview route reads the API key.
5. **Headers** (`server/plugins/preview.ts`, `buildPreviewHeaders()` in `server/utils/preview.ts`): every response to a preview request (a path under `/api/preview`, or any URL with a `preview` query parameter: the URL decides, not a valid token) gets `Cache-Control: private, no-store`, `X-Robots-Tag: noindex, nofollow`, `Referrer-Policy: no-referrer`, and loses `CDN-Cache-Control`, `Vercel-CDN-Cache-Control` and `Surrogate-Control`. Applied on the `request` hook, on `beforeResponse` and on `render:response`; the preview routes set them themselves too, `routeRules` add `cache-control`/`x-robots-tag` for `/api/preview` and `/api/preview/**`, and both cdn-cache plugins skip `?preview`. While the preview is configured, the response also replaces the default `frame-ancestors 'self'` with `'self'`, the Payload origin and `NUXT_PAYLOAD_PREVIEW_FRAME_ANCESTORS` (see Security headers; https origins only, `http://localhost` only in dev, no wildcards, invalid entries dropped).
6. **Payload** returns drafts only to an authenticated caller: an anonymous `?draft=true` gets the published version (Payload's `read` access, simple-landing-page-nuxt#26). A wrong API key also gets the published version, without an error: when a preview shows no drafts, check the key first.

Not configured (empty or short secret, empty API key): `/api/preview/**` is a 404 (still `no-store`), and `?preview` pages keep the default `frame-ancestors`. Never log the token or the API key or put them in a `captureError()` context (`SENSITIVE_KEY` filters `token`/`api_key`, and `SECRET_PATTERNS` mask JWTs and `API-Key <key>`).

**In the browser** (`app/plugins/preview.client.ts`, `usePreview()` in `app/composables/preview.ts`, helpers in `app/utils/preview.ts`, `previewRepository()`, `AppPreviewBanner`):

- **Token handover.** The plugin reads `#token=` and removes it from the address bar with `history.replaceState` (`removePreviewTokenFromAddressBar()`), also from vue-router's `history.state.current`, which the router would otherwise write back into the URL on the next navigation. It runs with `order: -25`, before `nuxt:router` (`enforce: 'pre'`, -20), which reads the URL when it is created, so the router, the route middleware and anything reading the route never see the token; a second pass on `app:created` covers the opposite order. `?preview=1` stays in the URL, so a reload is again `no-store` and frameable.
- **Where the token lives.** In `useState('preview')` (`{ status: 'active', token, expiresAt }`, client only) and in `sessionStorage` (`payload-preview`, `{ token, expiresAt }`): per tab, never sent to a server, gone with the tab, and a reload of the preview tab keeps the preview. Never a cookie, a query parameter or the SSR payload. The stored token is also used on a load without `?preview` (a client-side navigation drops the marker, a reload then has none); that page is the ordinary published render, the drafts again come only from the browser. It is removed on exit, on expiry and on a 401.
- **Start.** After hydration (`onNuxtReady`) the plugin calls `usePreview().start(token)`: `POST /api/preview/session` with the header, then `active`, or `expired` for a refused token, a session check without an answer, or a `?preview` page with no token at all. The state is `off` on the server and during hydration, so neither the server render (CDN-cached or not) nor the hydrated markup depends on it.
- **Drafts.** Every CMS composable goes through `useCmsAsyncData()` (`app/composables/cms.ts`), which switches the cache key to `<key>:preview` (`cms:navigation:pl:preview`) and passes `{ token }` to the fetcher together, from the same state, so a draft never lands under a published key; the key change makes Nuxt fetch the drafts. `fetchGlobal()` with a preview request calls `/api/preview/cms/<slug>` with `x-preview-token` and `cache: 'no-store'`, in the browser only. Without a token (expired) it fetches nothing, never the published version. A 401 is thrown as `createPreviewUnauthorizedError()` (a new error, without the request and its token header); the composable calls `expire()` and renders no section. A draft that doesn't match its schema is not reported, since Payload saves drafts without validating them (its default `versions.drafts.validate: false`), and its section is hidden, as it would be when published.
- **Expiry.** A timer sets `expired` at `expiresAt`, before a request gets the 401. While `expired` the keys stay `:preview`: drafts already loaded stay, sections that weren't loaded stay empty, and nothing falls back to the published content, a silent fallback the editor would take for the draft. The banner says so and offers the exit.
- **Banner.** `AppPreviewBanner` (`app/components/app/preview-banner.vue`, in `app.vue` above every layout): an `aside` labelled "Draft preview" with a `role="status"` line (active, with the end time, or expired) and an "Exit preview" button. Rendered only while the state is not `off`, so never on the server. No design exists; it uses `bg-color-accent` to stand apart from the ink announcement bar.
- **Exit.** `usePreview().exit()` first clears the `:preview` entries (`clearNuxtData(isPreviewCacheKey)`): Nuxt starts a new key from the old key's data, so without it the published key would hold the draft until the published fetch returned. Then it resets the state and `sessionStorage` and drops `?preview` with `router.replace` (no reload, so it also works in Payload's frame, where a page without `?preview` can't be framed); the composables then fetch the published content.
- **Live Preview.** In Payload's Live Preview frame (or a window it opened), the plugin posts `{ type: 'payload-live-preview', ready: true }` to the Payload origin (`NUXT_PUBLIC_PAYLOAD_URL`'s origin, never `*`), and on a `payload-document-event` message from that origin and that window it refetches the `:preview` keys (debounced 300 ms). The message content isn't used, and Payload's unsaved form state isn't merged in: the preview shows the last saved draft (autosave makes that close to live).
- **Sentry.** The browser side reports only a request without an answer (`previewRepository()`: `source: 'preview'`; a draft: `source: 'payload'`, `cms_global`, `draft: true`), always as a new `Error` without a `cause`, because the fetch error carries the request headers and so the token.
- Tests: `tests/unit/utils/preview.test.ts`, the draft cases in `tests/unit/repository/cms.repository.test.ts`, `tests/unit/repository/preview.repository.test.ts`, `tests/nuxt/composables/preview.test.ts` (keys, 401, exit; fails if the exit stops clearing the drafts first or the key stops changing) and `tests/nuxt/components/preview-banner.test.ts`. `removePreviewTokenFromAddressBar()` is unit tested; the plugin's wiring (its order before the router, the timer, `postMessage`) is not covered by an automated test.

### `routeRules` / rendering

`nuxt.config.ts` forces SSR (`{ ssr: true }`) for `/**/products/**`, `/**/collections/**`, `/**/categories/**`, `/**/account`, `/**/store`, `/**/cart`, `/**/checkout` — keep new commerce-critical routes consistent with this if they need SEO/SSR. Nuxt 4.6 also declares `ssr` in generated Nitro route-rule types, so the old local augmentation is no longer needed.

Catalog pages (the `/[countryCode]` home, `store`, `products/[handle]`, `categories/[handle]`, `collections/[handle]`) and `search` opt into the CDN cache with `definePageMeta({ cdnCache: true })`. `search` is not indexed (`noindex, follow`, see SEO) but is cached all the same: its render depends only on the URL (`?q=`, `?page=`), never on a cookie. The CDN keys the cache by the full URL, so every distinct `?q=` is a separate entry anyone can create; that only costs cache space, since each entry is the same public render for everyone. `app/plugins/cdn-cache.server.ts` marks such requests and `server/plugins/cdn-cache.ts` adds `CDN-Cache-Control: max-age=60, stale-while-revalidate=300`, but only to `200` responses without `Set-Cookie`, so redirects, errors and personalised responses are never shared. A page that failed is never marked, and neither is the error page Nitro renders for it: that is a request of its own to `/__nuxt_error` for the failed URL, so it resolves the same opted-in route and reaches the render hook with status `200`; the real status (a 500, or the 404 of `useNotFoundWhenMissing`) is applied afterwards to the response that carries the page, which no hook sees. So `app/plugins/cdn-cache.server.ts` skips a render with `payload.error` or `ssrContext.error`, and `server/plugins/cdn-cache.ts` skips the `/__nuxt_error` request itself (#66). Nor is a page whose data didn't load (#75): a failed `useLazyAsyncData` doesn't fail the render, so with Medusa down (or regions still in the Nitro cache and the catalog calls failing) the home, store, category, collection and search pages answer `200` with empty sections. The page plugin skips a render with any entry set in `payload._errors` (Nuxt's per-key async-data errors), so such a page is still served but never shared; the status stays `200` on purpose, because a 5xx would mean deciding per page which data is essential. A missing handle is not a failure (its fetch succeeds with `null`) and keeps its 404 from `useNotFoundWhenMissing`. Payload failures don't count: `fetchGlobal()` returns `null` without an error, so a page with a missing CMS section is still shared. Neither shares a preview request (`?preview`, see "Draft preview"): both skip it, and `server/plugins/preview.ts` makes it `private, no-store` and strips any CDN header. A page that opts in must render the same for every visitor on the server: no cookie reads or writes during SSR, and anything per-visitor (cart, account state) stays client-only (`<ClientOnly>`). `useFetchCustomer()` follows this by itself (browser only on a `cdnCache` page, see the session contract above); a new fetcher that forwards cookies with `useRequestFetch()` must do the same. Don't opt in cart, checkout, account or order pages.

- Don't prerender catalog pages instead: that froze product data (`_payload.json`) at build time, so catalog changes in Medusa only showed up after a storefront redeploy.
- Don't use `isr`/`swr` route rules for them either: Nitro's Vercel ISR only handles literal path prefixes (ours start with a dynamic country code) and doesn't pass the query string (`page`, `sortBy`) to the render.

### Security headers (framing)

`server/plugins/frame-ancestors.ts` sets `Content-Security-Policy: frame-ancestors 'self'` on every response, so no other site can embed the storefront, cart, checkout and account pages included (clickjacking). It restricts nothing else: `frame-ancestors` has no fallback to `default-src`, so scripts, images, Stripe and the InPost Geowidget are unaffected, and nothing in this repo frames the storefront. Stripe 3DS, BLIK and Przelewy24 work the other way round (their pages are framed by, or redirect back to, ours), which this policy doesn't limit.

- **A default set on the `request` hook, not at write time**, so it also covers API routes, errors, redirects and Nitro's static asset handler, and never touches `CDN-Cache-Control`, `Set-Cookie` or the status (the CDN cache plugin is unchanged). On Vercel the static files in `.output/public` are served by the CDN without running the function, so they don't carry it; they aren't documents and can't be framed in a way that matters.
- **A response that needs another policy replaces the header** with `setResponseHeader(event, 'content-security-policy', ...)` and then owns the whole value, `frame-ancestors` included. The draft preview (#53, `server/plugins/preview.ts`) does exactly that, listing `'self'`, the Payload origin and the Medusa admin origins from `NUXT_PAYLOAD_PREVIEW_FRAME_ANCESTORS` (both are listed because the frames are nested and every ancestor is checked), for preview responses only and only while the preview is configured. Its plugin runs after this one (plugins load in file order), so it replaces the default rather than being kept out by it. Don't append a second `Content-Security-Policy` to relax it: browsers enforce every policy, so the intersection with `'self'` would still block the frames. A response that sets its own policy without `frame-ancestors` loses this default, so include it.
- Nitro's own error handler replaces the header with `script-src 'none'; frame-ancestors 'none'` (and `X-Frame-Options: DENY`) on JSON error responses, which is stricter, and adds `X-Frame-Options: DENY` to rendered error pages. Nothing is duplicated, and the stricter error value is fine.
- **No `X-Frame-Options`** from us: every current browser enforces `frame-ancestors` and ignores `X-Frame-Options` when it is present, so the old header would only help ancient browsers and would be one more header the preview has to override.
- Not configured in `routeRules.headers`: Nitro's Vercel preset compiles those into Vercel's routing config (applied by the platform, not by the function), and whether a header the function sets itself can still override them there isn't verified, which the preview needs. The plugin is the same on every host and testable.

### SEO (sitemap, robots.txt, canonical/hreflang, structured data)

- **Sitemap**: `@nuxtjs/sitemap` (9.1.x, the Nuxt 4-compatible line) serves `/sitemap.xml` from a single source, `server/api/__sitemap__/urls.get.ts`: it reads the countries from the cached `/api/regions` handler and walks Medusa's product/category/collection lists (`listAllPages`, `server/utils/pagination.ts`) via `medusaRepository().listSitemapCatalog()` (`server/repository/medusa.repository.ts`), then `buildCatalogSitemapUrls()` (`app/utils/seo.ts`) emits home, store and every product/category/collection page per country. The source is a `defineCachedEventHandler` (10 min, SWR), on top of the module's own 10-minute source cache; failures aren't cached. The `pages/` scan is off (`excludeAppSources: true`). A new indexable page type must be added to `buildCatalogSitemapUrls()`.
- **robots.txt**: `server/routes/robots.txt.ts` (there is no `public/robots.txt`), rules in `server/utils/robots.ts`: disallows cart, checkout, account, wishlist and order pages for every country and points to the absolute sitemap URL. Those pages also carry `robots: noindex`.
- **Canonical + hreflang**: `useCountrySeoLinks()` (`app/composables/seo.ts`) on every indexable page (home, store, product, category, collection) adds the canonical link, one `hreflang` alternate per region country and `x-default` (= `appConfig.defaultCountry`), plus `og:url`. hreflang is `<locale>-<COUNTRY>` with the locale from `getLocaleFromCountryCode()`, the same mapping the region middleware uses for i18n (`pl-PL`, `en-DE`, …). Only `?page=N` (N > 1) is kept in those URLs; sorting and other params share the canonical. By-handle pages pass `() => !!data.value` so their 404 doesn't emit a canonical. Countries come from the `countries` payload the middleware loaded; nothing reads cookies, so CDN-cached pages stay shareable.
- **Product JSON-LD**: `useProductJsonLd()` renders `buildProductJsonLd()` (`app/utils/structured-data.ts`) as `application/ld+json`: one `Offer` per variant priced in the page's region (`calculated_amount`, currency, availability from `getVariantAvailability()` — the same helper the add-to-cart button uses). Never add facts Medusa doesn't provide (brand, ratings, condition). `nuxt-schema-org` isn't used: Nuxt 4.6 ships Unhead 3, so the former compatibility concern is gone; the hand-written Product/Offer JSON-LD keeps this narrow schema explicit without another module.
- **Not indexed**: cart, checkout, account, wishlist and order pages (`noindex` + disallowed in robots.txt) and `/search` (`noindex, follow`: thin, endless `?q=` URLs; deliberately _not_ disallowed, so crawlers see the noindex). None of them call `useCountrySeoLinks()` or appear in the sitemap.
- **`<html lang>`**: set in `app/app.vue` from the i18n locale (`pl`/`en`), which the region middleware sets from the URL's country only — identical for every visitor, updated on client-side navigation. Not via `@nuxtjs/i18n`'s `useLocaleHead()`: it needs a `language` on every locale and logs a missing-`baseUrl` warning on every render with this `no_prefix` setup.

### Directory layout

- Imports use root aliases, never relative paths: `~/` for `app/` (also from `tests/`), `~~/` for the project root (e.g. `~~/server/...`). ESLint enforces it (`no-restricted-imports` in `eslint.config.mjs`, for `app/`, `server/`, `tests/`; dynamic `import()` is not checked). Details: `.claude/skills/nuxt-vue-architecture/SKILL.md` -> `## Imports`.
- `app/pages` — file-based routes, all nested under `[countryCode]`.
- `app/components` — organized by domain (`cart`, `checkout`, `product`, `order`, `collection`, `store`, `auth`, `app`, `wishlist`), with further subfolders for compound UI (e.g. `checkout/address`, `checkout/payment`, `cart/item`).
- `app/composables` — one file per domain (`cart`, `category`, `checkout`, `cms`, `collection`, `country`, `customer`, `filters`, `medusa` (`useMedusaClient()`), `order`, `payment`, `preview`, `product`, `wishlist`), plus `not-found` shared by the by-handle pages and `seo` (canonical/hreflang, product JSON-LD). These call into `app/services` and/or `app/repository` rather than Medusa directly (see above).
- `app/services` — `*.service.ts` business-logic layer between composables and repositories (cart, category, cms, collection, customer, order, payment, product). See the repository → service → composable note above for which ones actually have callers.
- `app/repository` — `*.repository.ts` data-access layer; `api.repository.ts` provides the shared `useMedusaClient()` + error-handling wrapper the other repositories (product, category, collection, country, order, payment, cart, customer) build on; `stripe.repository.ts` is the Stripe.js counterpart; `cms.repository.ts` is the Payload counterpart (see Payload CMS integration above) — it calls the `server/api/cms` proxy with `$fetch`, not through `apiRepository()`, since that wrapper is Medusa-specific (in the draft preview it calls `/api/preview/cms` instead); `preview.repository.ts` checks the preview token (`/api/preview/session`).
- `app/utils` — pure helpers (`price`, `product`, `address`, `country`, `link`, `medusa` (the page client's config), `medusa-response` (`parseMedusaResponse()`, also imported by `server/repository`, so it imports its own dependencies), `payment`, `percentage-diff`, `homepage`, `seo`, `structured-data`, `preview`), auto-imported by Nuxt, plus `capture-error` and `sentry` (see Error reporting). `seo.ts` is also imported by the sitemap source in `server/`, so it imports its own dependencies explicitly.
- `server/repository` — `*.repository.ts`, one per external boundary (today `payload.repository.ts`, `medusa.repository.ts` for regions and the sitemap, and `customer.repository.ts` for Medusa's customer/auth calls; see Server layers). Imported explicitly with `~~/server/repository/...`.
- `server/api` — Nitro route handlers for `customers`, `regions`, `cms` and `preview` (the draft preview: entry, session, drafts); `__sitemap__/urls` feeds `/sitemap.xml` (see SEO). Catalog repositories call Medusa directly rather than through local product/category/collection handlers.
- `sentry.client.config.ts`, `sentry.server.config.ts` — Sentry init for the `@sentry/nuxt` module; they must stay at the project root (see Error reporting).
- `server/routes/robots.txt.ts` — `/robots.txt` (see SEO).
- `server/utils/handler.ts` / `server/types/medusa-error.ts` — shared error-wrapping for API routes.
- `server/utils/validation.ts` — `parseRequestInput()`, the zod request-input parser every handler uses (see Server API routes).
- `server/utils/cms.ts` — slug/query validation for the Payload proxy (`robots.ts`, `pagination.ts` are the other pure, unit-tested helpers there).
- `server/utils/preview.ts` / `preview-token.ts`, `server/plugins/preview.ts`, `app/types/preview.ts` — the draft preview (config, headers, token check, request schemas; see "Draft preview"). Its browser side: `app/plugins/preview.client.ts`, `app/composables/preview.ts`, `app/utils/preview.ts`, `app/repository/preview.repository.ts`, `app/components/app/preview-banner.vue`. The preview tests share `tests/unit/server/preview-harness.ts`, which runs handlers and plugins on a real h3 app and mints tokens the way Payload does.
- `server/utils/session-cookie.ts` — the `medusa_jwt` session cookie: reading the token, its attributes and lifetime (see Server API routes).
- `server/utils/medusa.ts` — `serverMedusaClient(event)`, the server routes' Medusa client (see Server layers); its page-side counterpart is `app/plugins/medusa.ts`.

### Test runner boundary

`@nuxt/test-utils` is used only for the Vitest Nuxt unit/integration project. The real-browser e2e suite (issue #45) runs on `@playwright/test` (pinned, like Vitest), for the Chromium/WebKit/Firefox matrix, independent traces and a `webServer` lifecycle. Don't use `@nuxt/test-utils/e2e`: `vitest.config.ts` sets `NUXT_TEST_UTILS`, which strips the Sentry, image and sitemap modules from the Nuxt config, and the CDN-cache/SSR rules only exist in a production build.

- **Layout.** Specs in `tests/e2e/specs/<area>/*.spec.ts` (never matched by Vitest), helpers as plain functions in `tests/e2e/support/` (`env.ts`, `test-data.ts`, `payload-stub.ts`, `fixtures.ts`, `network-guard.ts`, `page-errors.ts`, `safety.ts`), config in `playwright.config.ts`. Imports use `~~/` and `~/` like everywhere else. `waitForTimeout` is an ESLint error; wait for an assertion, a response or `expect.poll`. Selectors are roles, labels and visible text (copy from `i18n/locales/*.json` or the stub), `data-testid` only where no semantic selector is stable. Use the `gotoHydrated` fixture from `~~/tests/e2e/support/fixtures` instead of `page.goto` before interacting: it waits for `useNuxtApp().isHydrating === false`.
- **App under test.** `playwright.config.ts` runs `pnpm build && pnpm preview` as its `webServer` (so the build happens in one place, with one environment), health-checks `/robots.txt` and tests `http://127.0.0.1:3100`. `E2E_SKIP_BUILD=1` reuses `.output` for local iteration (it is then your job to know it was built with the current e2e environment), `E2E_VERBOSE=1` shows the build log, `E2E_ALL_BROWSERS=1` adds Firefox and WebKit.
- **Environment.** The suite reads only `E2E_*` variables (`E2E_MEDUSA_BACKEND_URL`, `E2E_MEDUSA_PUBLISHABLE_KEY`, `E2E_STRIPE_KEY`, `E2E_APP_PORT`, `E2E_PAYLOAD_STUB_PORT`, catalog handles in `test-data.ts`) and sets every variable the build reads (`appEnv` in `env.ts`), empty ones included, so neither a shell's `NUXT_PUBLIC_*` nor `.env` reaches the e2e build. The Medusa URL and the image host list are build-time values (see Environment), which is another reason the build lives in the `webServer`. `assertSafeE2eEnvironment()` stops the run before any build with a `pk_live_` Stripe key, a Medusa/Payload URL on a production host (`PRODUCTION_HOST_MARKERS` in `safety.ts`) or a Sentry DSN/auth token (also when only set in the calling shell). Add a new production host there. Never point the suite at production data; Vercel previews must not use the production Medusa either.
- **Backends.** Payload is always the local stub (`startPayloadStub()`, started by `globalSetup`), which serves the shapes of `tests/fixtures/cms.ts` with the handles from `test-data.ts` and, like the real Payload, **sends no CORS headers**. Medusa is the only real backend: specs that need it carry `{ tag: '@medusa' }` (Stripe: `@stripe`) and are left out through `grepInvert` while `E2E_MEDUSA_BACKEND_URL` (`E2E_STRIPE_KEY`) is unset, so `pnpm test:e2e` still passes with the backend-free specs. In GitHub Actions that Medusa is ephemeral: `e2e.yml` runs medusaDemo's `e2e-medusa` composite action (PostgreSQL and Redis in Docker, migrations, the deterministic e2e seed, Medusa on `127.0.0.1:9100`) and passes its `backend-url`/`publishable-key` outputs as `E2E_MEDUSA_*`; the publishable key is new on every fresh database, so never hard-code it. Locally, start the same Medusa as described in medusaDemo's `docs/e2e.md` (Docker needed). The seed's handles, titles and prices are mirrored in `test-data.ts`; the seed has no product images on purpose, and `trackPageErrors()` (`page-errors.ts`) makes a page that throws or requests a broken image fail. Payment flows use Stripe test mode and InPost's sandbox, never production keys; Stripe isn't configured in CI yet, so `@stripe` specs don't run there.
- **Retries and artifacts.** Retries only on CI (1); a test that passes on retry is reported as flaky, not hidden. `trace: 'on-first-retry'`, `screenshot: 'only-on-failure'`; reports go to `playwright-report/`, artifacts to `test-results/` (both git- and Prettier-ignored).
- **The #42 regression** (`specs/home/cms-sections.spec.ts`, `@medusa`) is guarded by `trackPayloadRequests()`: the browser must never call Payload itself, only `/api/cms`. It fails when `fetchGlobal()` is changed back to call Payload directly.

### Key modules (`nuxt.config.ts`)

`@nuxt/ui` (with `colorMode: false`), `@nuxt/image`, `@nuxt/eslint` (stylistic rules enabled), `@nuxtjs/sitemap` (pulls in `nuxt-site-config`; see SEO). Nuxt 4.6.3-compatible releases are used for Sitemap 9.1, Image 2.2, ESLint 1.17, i18n 10.6 and Sentry 11.10. The Medusa SDK (`@medusajs/js-sdk`, pinned to the same version as `@medusajs/types`) is used without a module since #89 (`@nuxtjs/medusa` 1.2.0 was unmaintained): `app/plugins/medusa.ts` provides the page's client (`$medusa`, read through `useMedusaClient()`), `server/utils/medusa.ts` the server routes' (`serverMedusaClient(event)`), both from `runtimeConfig.public.medusa`. It needs no `build.transpile` or `optimizeDeps` entry: Vite pre-bundles it, with its CommonJS `qs`, in dev, and Nitro bundles it; the former `optimizeDeps.include: ['qs']` was needed only because the module transpiled the SDK. `@nuxt/ui` remains at 3.0.0 to keep this issue from expanding into its major v4 component/API migration: Nuxt UI is used in 54 Vue files, and the v4 guide documents renamed/removed components and form behavior changes. Its v3 build succeeds on Nuxt 4.6.3; migrate UI separately with visual review. `jose` (pinned to 6.2.13, the library Payload signs with) is used only on the server, by `verifyPreviewToken()`. Stripe is integrated via `@stripe/stripe-js` using `runtimeConfig.public.stripeKey`, only through `stripe.repository.ts`; the review step's payment flow (card, BLIK, Przelewy24 redirect and return) lives in `useCartPayment()` (`app/composables/payment.ts`). `@nuxt/icon` (installed by Nuxt UI) puts only the `lucide` and `flag` collections into the server function; every other icon must appear as a literal name in the source so the client-bundle scan picks it up. An icon name built at runtime from another collection won't render unless that collection is added to `icon.serverBundle.collections`. Don't enable `i18n.bundle.dropMessageCompiler`: with it every server render fails with `unhandled node type: 0`. `h3` is a devDependency pinned to the exact version Nitro uses at runtime (1.15.11, same as `nitropack`/`@nuxt/nitro-server` in the lockfile): the repo uses `shamefully-hoist` and `@nuxt/test-utils` has an optional h3 2.x peer, so without the pin `node_modules/h3` could be 2.0.8 and the server tests (`createError`, `isError`) would assert against an h3 that production doesn't use. Bump it together with Nitro, to whatever version `pnpm why h3` shows for `nitropack`.
