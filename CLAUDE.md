# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A headless e-commerce storefront ("Fashion Store") built with Nuxt 4.6.3 against a Medusa.js commerce backend. It is based on https://github.com/OlivierBelaud/nuxt-starter-medusa. Requires a supported Nuxt Node.js version (`^22.22.3 || ^24.15.0 || >=26.0.0`) and pnpm >= 9 (pinned to 11.5.0 by `packageManager`), plus a running Medusa backend.

## Commands

```bash
pnpm install       # install deps (postinstall runs `nuxt prepare`)
pnpm dev           # start dev server
pnpm build         # production build
pnpm generate      # static generation
pnpm preview       # preview a production build
pnpm lint          # eslint .
pnpm lint:fix      # eslint . --fix
pnpm format        # prettier --write .
pnpm format:check  # prettier --check .
pnpm test          # vitest run --typecheck
```

The Vitest unit tests live under `tests/unit/`; `pnpm test` runs them and Vitest’s TypeScript checker against the project `tsconfig.json`, covering the test files, their imported source graph and Nuxt-generated auto-import types. CI runs them together with `pnpm lint`, `pnpm format:check` and `pnpm build` on pushes to `main` and pull requests. Run one test file with `pnpm exec vitest run --typecheck tests/unit/utils/product.test.ts`.

### Environment

Copy `.env.template` to `.env` and set:

- `NUXT_PUBLIC_MEDUSA_BACKEND_URL` — Medusa backend base URL (default `http://localhost:9000`)
- `NUXT_PUBLIC_MEDUSA_PUBLISHABLE_KEY` — Medusa store publishable API key
- `NUXT_PUBLIC_STRIPE_KEY` — Stripe publishable key
- `NUXT_PUBLIC_INPOST_GEOWIDGET_TOKEN` — InPost Geowidget token for the parcel locker picker in the delivery step
- `NUXT_PUBLIC_PAYLOAD_URL` — Payload CMS base URL (editorial/marketing content; see Payload CMS integration below). All editorial content (header nav, footer links/contact, home sections and their images) comes only from Payload; there is no static fallback, so the sections that need it are not rendered while it is unset or unreachable.
- `NUXT_PUBLIC_SITE_URL` — public origin of the storefront (e.g. `https://shop.example.com`), read by `nuxt-site-config` (installed by `@nuxtjs/sitemap`) for canonical/hreflang links, `sitemap.xml` and `robots.txt`. Optional — falls back to the request origin, so set it in production to keep preview/alias hosts out of canonical URLs.
- `NUXT_PUBLIC_SENTRY_DSN` — Sentry DSN (public by design; see Error reporting). Optional: empty means Sentry is off and errors only go to the console. Use the same Sentry organization as the Medusa backend and admin (damiankrupa1/medusaDemo#18), as its own project. Related, all optional: `SENTRY_DSN` (server-only DSN, defaults to the public one), `NUXT_PUBLIC_SENTRY_ENVIRONMENT` (defaults to Vercel's `VERCEL_ENV`, then `NODE_ENV`), `NUXT_PUBLIC_SENTRY_RELEASE` (defaults to `VERCEL_GIT_COMMIT_SHA`), `NUXT_PUBLIC_SENTRY_TRACES_SAMPLE_RATE` (0-1; empty keeps tracing off).
- `SENTRY_ORG`, `SENTRY_PROJECT`, `SENTRY_AUTH_TOKEN` — build-time only, for the source map upload. Keep them in Vercel/CI secrets, never as `NUXT_PUBLIC_*`. Without `SENTRY_AUTH_TOKEN` no source maps are generated or uploaded.

### Git hooks (husky)

- `pre-commit` runs `pnpm lint` (`eslint .` on the whole project, not only staged files) and blocks the commit on failure. That is all it does: `package.json` has a `lint-staged` config (`eslint --fix` + `prettier --write` on `*.{js,ts,vue}`, `prettier --write` on `*.{json,css,scss,md}`), but no hook calls it, so nothing formats or auto-fixes staged files. Run `pnpm format:check` / `prettier --write <files>` yourself.
- `commit-msg` runs commitlint (`@commitlint/config-conventional` + `commitlint.config.js`). Commit subjects must use `type: description` with `type` restricted to `feat|fix|refactor|docs|style|test|build`, a non-empty subject, max 72 chars. The hook prints commitlint's errors but does not block the commit (the script ends without `exit 1`, so it always exits 0), so check its output yourself.

## Architecture

### Three-layer data access: repository → service → composable

Most Medusa Store API access flows through three layers under `app/`:

1. **Repository** (`app/repository/*.repository.ts`): thin data-access functions. `apiRepository()` wraps `useMedusaClient()` (from `@nuxtjs/medusa`) with a `request()` helper that reports (`captureError`) and rethrows errors; the `product`, `category`, `collection`, `order`, `payment`, and `cart` repositories all call `apiRepository()` and issue `client.store.*` calls directly. `customer.repository.ts` and `country.repository.ts` are the exceptions: they call `server/api/customers/**` and `server/api/regions` via `$fetch` (still funneled through `apiRepository()`'s `request()`), because auth needs the server-side cookie session and regions are cached on the server. `stripe.repository.ts` wraps Stripe.js instead of Medusa (lazy `loadStripe`, card element, card/BLIK/Przelewy24 confirmations, PaymentIntent lookup) and turns Stripe's `{ error }` results into thrown errors, reporting all but the customer-side ones (`card_error`, `validation_error`).
2. **Service** (`app/services/*.service.ts`): composes repository calls and adds business logic. `cart.service.ts`, `customer.service.ts` and `payment.service.ts` carry real logic (cart-id lifecycle, region reconciliation, `refreshNuxtData` side effects; for payment, picking the Stripe confirmation by provider and checking the payment Przelewy24 redirected back from) and are consumed by composables. `category.service.ts`, `collection.service.ts`, `order.service.ts`, and `product.service.ts` are currently thin pass-throughs with **no callers** — the composables for those domains call the repository directly instead. If you touch one of those domains, either wire the composable through its service (so the layer earns its keep) or remove the unused service — don't add a fourth pattern.
3. **Composable** (`app/composables/*.ts`): the Vue-facing layer. Wraps repository/service calls in `useLazyAsyncData`/`useLazyFetch` for reads (see cache-key convention below), or a `loading`/`data`/`mutate()` shape for writes.

**Server API routes** (`server/api/**`): Nitro/H3 handlers using `serverMedusaClient(event)` (from `#medusa/server`), wrapped in `defineWrappedResponseHandler` (`server/utils/handler.ts`), which catches thrown errors, extracts `MedusaError` `status`/`message`, and re-throws as an H3 error (an error that already is an H3 error, like a validation 400, passes through unchanged). Only `server/api/customers/**` (login/register/logout/me, for the server-side cookie session), `server/api/regions` (a `defineCachedEventHandler`, since the region middleware needs regions on every server render) and `server/api/cms/[slug]` (the Payload proxy, see Payload CMS integration; not Medusa, so it is not wrapped in `defineWrappedResponseHandler`) are called from `app/` today.

- **Request input is parsed with zod**: every handler passes its body (`readBody`), query (`getQuery`) and route params (`getRouterParams`) through `parseRequestInput(schema, input, part)` (`server/utils/validation.ts`) and only uses what it returns. Invalid input is a `400` (`message: 'Invalid request body'`, `data: z.flattenError(...)`), never a Medusa error or a 500. The schemas live in `app/types/<domain>.ts` next to their inferred types, never inline in a handler: a form's schema is the request schema (`buildSigninSchema(t)` in the form, `signinRequestSchema = buildSigninSchema()` with zod's English messages on the server), so there is one definition per form. Query schemas are whitelists (`productListQuerySchema` in `app/types/catalog.ts`): unknown parameters are dropped, `limit` is clamped, and `fields` stays server-controlled, so a caller can't widen what is sent to Medusa. h3's `readValidatedBody`/`getValidatedQuery` aren't used: they wrap the thrown error in a second one, which buries the issues.
- **Medusa responses are not validated at runtime**, deliberately: Medusa is our own backend, its responses are typed by `@medusajs/types` pinned to the same version as the SDK, and a full schema of carts/products/customers would duplicate those types and fail on every harmless Medusa addition. A shape change shows up when the SDK/types are bumped, which is when to check it. Payload responses are validated (see Payload CMS integration), because Payload is edited by hand and its contract lives only in the `payload-backend-todo` skill. `server/api/products`, `categories`, and `collections` handlers still exist but are currently unreferenced from `app/` — the equivalent repositories call `client.store.*` straight from the client/SSR context instead. Treat those handlers as dead code / cleanup candidates, not the active path for those domains.

When adding a new Medusa-backed feature: put the client call in a repository, put any orchestration/business logic in a service, and expose it to components via a composable. Don't call `useMedusaClient()` or `$fetch` directly from a composable or component.

### Region/country routing

Every page lives under `app/pages/[countryCode]/...`; `app/pages/index.vue` is just a redirect target. `app/middleware/region.global.ts` runs on every navigation (on the server, and in the browser during hydration and client-side navigation) and:

- Takes the country from the `countryCode` route param when it's a known region. The URL alone decides, never the cookie, so a server-rendered page is the same for every visitor (see `routeRules` / rendering).
- Otherwise redirects to `/${iso_2}${fullPath}`, using the `country_code` cookie's country if it's still a region, else `useAppConfig().defaultCountry`.
- Calls `useCountry().setCountry(...)` to sync `useState('country')` and the i18n locale. The `country_code` cookie is only written in the browser, so SSR responses never carry `Set-Cookie`.

`useCountry()`/`useCountries()` (`app/composables/country.ts`) are the source of truth for the current region; most data-fetching composables key off `country.value.region_id`.

### Internal links

Links inside the store never hard-code the country prefix; `AppLink`/`AppLinkButton` (and, outside them, `useCountryLink()` for a `UButton :to`, or `toCountryLink()` for `navigateTo`) add it from `useCountry()`. Their `to` takes two forms (`AppLinkTarget`, `app/types/link.ts`):

- **A route with params → named route** without `countryCode`: `:to="{ name: 'countryCode-products-handle', params: { handle } }"`. `experimental.typedPages` generates the route names, so a misspelled name or a missing param is a type error, and pages read their params through `useRoute('countryCode-products-handle')`. Guard an optional param (`product.collection?.handle ? { ... } : undefined`); a named route with an empty param resolves to no link instead of throwing.
- **A static page or a CMS/fallback URL → path string** relative to the country: `to="/store"`, `:to="link.url"`. Payload hands out arbitrary URLs, and CMS-provided URLs are always `to: string`.

Type a country-relative named route with `AppRoute` from `~/types/link`: it deliberately omits the required `countryCode` param and matches the `AppLink` contract. Do not rely on the root `RouteLocationRaw` here: Nuxt 4.6.3 uses Vue Router 5.4 while the root `vue-router` is 4.5.0 through `@nuxt/ui` 3.0.0, so their generated route types are not interchangeable.

### Data-fetching conventions

- Read operations use `useLazyFetch`/`useLazyAsyncData` with explicit, colon-delimited cache keys that encode the params they depend on (e.g. `` `products:${collection_id}:${category_id}:${limit}:${offset}:${region_id}` `` , `` `product:${handle}:region:${region_id}` ``). When adding a new fetcher, follow this key convention so `refreshNuxtData`/payload lookups keep working.
- By-handle repository lookups (product, category, collection) return `null` when nothing matches; their pages call `useNotFoundWhenMissing(data, status, message)` (`app/composables/not-found.ts`) so a missing handle answers a real 404 instead of an empty page, on the server and after client-side navigation.
- `useFetchProductByHandle` (`app/composables/product.ts`) has a `default()` that scans other cached `products:*` payload entries for a matching handle to avoid a network round-trip — be aware of this when changing product list cache keys.
- Cart/order/payment/customer mutation composables all follow the same shape: `loading` ref + `data` ref + async `mutate(...)`, and call `refreshNuxtData('cart')` / `refreshNuxtData('customer')` after any mutating call (done inside the service, e.g. `cart.service.ts`, `customer.service.ts`).
- Cart identity is a `cart_id` cookie managed by `useUserCart()` (90-day maxAge), not Medusa session state. Carts are created on the first add to cart (`updateOrCreateLineItem`); `useFetchCart()` only retrieves one and returns `{ cart: null }` before that, so treat `null` as an empty cart and `undefined` as still loading.

### Error reporting

Errors are reported once, where they come from an external system, through `captureError()` (`app/utils/capture-error.ts`): `apiRepository()`'s `request()`, `stripeRepository()`, the InPost Geowidget loader, `cms.repository.ts`'s `fetchGlobal()` (Payload: a failed request, or with `type: 'invalid_response'` a global that doesn't match its schema, reported once per distinct failure per server instance or page load via `shouldReportOnce()` in `app/utils/report-once.ts`, because it would otherwise repeat on every render; the event lists the zod `issues` as paths, codes and messages in `extra`, never the received content), Medusa's `type: 'cart'` answer in `usePlaceOrder()`, and `defineWrappedResponseHandler()` for the server API routes. Composables and components don't log errors; they only turn them into UI state. Don't name it `reportError` — that's a browser global.

`captureError(error, context)` is the only place that talks to Sentry (`@sentry/nuxt`, which supports Nuxt >= 3.7 and so Nuxt 4.6.3; `@sentry/vue` + `@sentry/node` would mean wiring the Nitro hooks by hand). Call sites don't change when the setup does.

- **Off without a DSN.** `sentry.client.config.ts` / `sentry.server.config.ts` (project root, loaded by the `@sentry/nuxt/module` in `nuxt.config.ts`) call `Sentry.init` only when `buildSentryOptions()` (`app/utils/sentry.ts`) gets a DSN. Without one `captureError()` only logs to the console, as before, and so do local dev and tests (`tests/setup.ts` mocks `@sentry/nuxt`). With a DSN it logs to the console in development only.
- **Context becomes tags.** `source` -> `source`, `type` -> `error_type`, `code` -> `error_code`, `declineCode` -> `decline_code`, `global` -> `cms_global`; any other key goes to `extra`. Reuse these keys in new call sites. `server/utils/handler.ts` reports with `source: 'server-api'` and passes the original error as `cause`, so Sentry's Nitro hook doesn't report the rethrown H3 error again.
- **Expected errors don't alert.** `isExpectedError()` treats a 4xx from Medusa/h3 (except 408 and 429) and a Stripe `card_error`/`validation_error` as the shopper's to fix: they become an `info` breadcrumb on the next real event, not an event. The `@sentry/nuxt` module itself already skips Nuxt errors with a 3xx/4xx status (404 pages via `showError`) and Nitro errors below 500.
- **What the module covers by itself:** Vue/Nuxt component errors (`vue:error`, `app:error`), unhandled exceptions and rejections in the browser, and unexpected Nitro errors (SSR render errors, 5xx). Don't add a second hook for those. An error that is both passed to `captureError()` and then left uncaught can be reported twice.
- **Privacy** (shop: customers, addresses, cards). `sendDefaultPii: false`, and `scrubSentryEvent()` (`beforeSend`) drops the user, cookies (incl. `medusa_jwt`), request body and query string (the Przelewy24 return carries the PaymentIntent client secret), keeps only `user-agent`/`accept`/`accept-language`/`host` headers, masks e-mails, bearer tokens, JWTs, Stripe secrets and Medusa cart/order/customer ids in messages, URLs and breadcrumbs, and replaces the value of keys such as `email`, `phone`, `address`, `cart`, `customer`, `card`, `locker`, `token` in `extra` and breadcrumb data. SDK-generated `contexts` and stack frames are not filtered. Never put customer, cart, address or payment data in a `captureError()` context; the filter is a safety net, not a licence. Extend `SENSITIVE_KEY`/`SECRET_PATTERNS` in `app/utils/sentry.ts` (with a test) when a new kind of data appears.
- **Release/environment.** `release` is `VERCEL_GIT_COMMIT_SHA` (build time for the client, runtime for the server) and `environment` is `VERCEL_ENV`, unless the `NUXT_PUBLIC_SENTRY_*` overrides are set. Tracing is off unless `NUXT_PUBLIC_SENTRY_TRACES_SAMPLE_RATE` is set; every traced request adds function time and Sentry quota on Vercel, so start low.
- **Source maps.** With `SENTRY_AUTH_TOKEN` set at build time (`nuxt.config.ts` `sentry.sourcemaps.disable` is otherwise `true`), the module generates `hidden` maps (no `sourceMappingURL` in the bundles), uploads them for the release and deletes them from `.output` afterwards, so they are never served publicly. Not verified in CI yet; check one stack trace in Sentry after the first deploy with a token.

### Payload CMS integration

Editorial/marketing content with no commerce meaning — the header's `primaryNav`, the footer's help/world/legal links and contact/social details, and most of the home page (campaign hero, brands row, studio story, journal, and the Medusa-backed category-tiles/shop-the-look sections below), see `.claude/skills/missing-cms-content/SKILL.md` for what's left — is served by a separate Payload CMS instance via `app/repository/cms.repository.ts` → `app/composables/cms.ts`, following the same repository → composable shape as the rest of the app. Medusa remains the only source of truth for products/prices/stock/cart/orders; Payload never duplicates that data. Two sections (`CategoryTiles`, `ShopTheLook`) curate real catalog items by handle, so they go through `app/services/cms.service.ts` instead of straight from the composable to the repository — composing a Payload fetch with a Medusa category/product-by-handle lookup is exactly the "business logic between repositories" the service layer exists for (see the repository → service → composable note above). Every other CMS fetcher has no such cross-domain logic and skips the service layer, same as `category`/`collection`.

- Payload's globals are public read-only today, but Payload sends no CORS headers for the storefront, so the browser can't call it: server renders worked while every client-side navigation refetched from the browser, failed, and (via `fetchGlobal()`'s catch) made the section vanish. `cms.repository.ts`'s `fetchGlobal()` therefore calls the same-origin proxy `server/api/cms/[slug].get.ts` (slugs allow-listed by `CMS_GLOBAL_SLUGS` in `app/types/cms.ts`, `locale`/`depth` validated by `cmsGlobalQuerySchema` through `server/utils/cms.ts` (a 400 with the issues), `defineCachedEventHandler` 60s + SWR; a Payload failure is a 502 that `fetchGlobal()` reports once), which forwards to Payload's REST API using `runtimeConfig.public.payloadUrl` (env `NUXT_PUBLIC_PAYLOAD_URL`) — no admin/API key involved. A new Payload global must be added to `CMS_GLOBAL_SLUGS` (`fetchGlobal()` only takes a `CmsGlobalSlug`, so forgetting it is a type error). If Payload ever needs a key or a draft-preview secret, move it to a private runtimeConfig used by that proxy; callers don't change.
- Every global is parsed with its zod schema in `app/types/cms.ts` (`cmsNavigationSchema`, ...; the `Cms*` types are inferred from them, so schema and type can't drift), passed to `fetchGlobal()` by its fetcher. Every field is required unless the schema says otherwise; the exceptions are explicit: an image's `alt` (`''` when missing) and the footer's `contact`/`social` (each text `null` when empty, the whole group `null` when nothing is entered). Unknown fields (Payload's ids, timestamps) are stripped. A global that doesn't match, e.g. a renamed field or an image fetched with `depth=0`, is treated like a missing one below.
- A Payload outage, an unconfigured URL or an invalid global must never break a page: `fetchGlobal()` catches, reports via `captureError({ source: 'payload', ... })`, and returns `null`. There is deliberately **no static fallback content** (no i18n copy, no bundled images, no hard-coded handles): a component whose global is `null` renders nothing for that section (`v-if` on its root; for the footer columns and contact block, on the block itself), rather than erroring or showing stand-in content. Only fixed UI chrome that is not in the Payload contract (footer column headings, tagline, "shopping" column) stays in i18n. Don't re-add a fallback in a component; fix the content in Payload.
- Payload's image URLs may point at a bucket host (Payload's `S3_FILE_URL`) instead of the Payload origin. `nuxt.config.ts` allow-lists the Payload host plus the comma-separated hostnames in `NUXT_PUBLIC_PAYLOAD_IMAGE_HOSTS` for `@nuxt/image`; an unlisted host still renders but unoptimized.
- Cache keys follow the existing convention: `` `cms:navigation:${locale}` ``, `` `cms:footer:${locale}` ``.

### `routeRules` / rendering

`nuxt.config.ts` forces SSR (`{ ssr: true }`) for `/**/products/**`, `/**/collections/**`, `/**/categories/**`, `/**/account`, `/**/store`, `/**/cart`, `/**/checkout` — keep new commerce-critical routes consistent with this if they need SEO/SSR. Nuxt 4.6 also declares `ssr` in generated Nitro route-rule types, so the old local augmentation is no longer needed.

Catalog pages (the `/[countryCode]` home, `store`, `products/[handle]`, `categories/[handle]`, `collections/[handle]`) opt into the CDN cache with `definePageMeta({ cdnCache: true })`. `app/plugins/cdn-cache.server.ts` marks such requests and `server/plugins/cdn-cache.ts` adds `CDN-Cache-Control: max-age=60, stale-while-revalidate=300`, but only to `200` responses without `Set-Cookie`, so redirects, errors and personalised responses are never shared. A page that opts in must render the same for every visitor on the server: no cookie reads or writes during SSR, and anything per-visitor (cart, account state) stays client-only (`<ClientOnly>`). Don't opt in cart, checkout, account or order pages.

- Don't prerender catalog pages instead: that froze product data (`_payload.json`) at build time, so catalog changes in Medusa only showed up after a storefront redeploy.
- Don't use `isr`/`swr` route rules for them either: Nitro's Vercel ISR only handles literal path prefixes (ours start with a dynamic country code) and doesn't pass the query string (`page`, `sortBy`) to the render.

### SEO (sitemap, robots.txt, canonical/hreflang, structured data)

- **Sitemap**: `@nuxtjs/sitemap` (9.1.x, the Nuxt 4-compatible line) serves `/sitemap.xml` from a single source, `server/api/__sitemap__/urls.get.ts`: it reads the countries from the cached `/api/regions` handler and walks Medusa's product/category/collection lists (`listAllPages`, `server/utils/pagination.ts`) via `serverMedusaClient`, then `buildCatalogSitemapUrls()` (`app/utils/seo.ts`) emits home, store and every product/category/collection page per country. The source is a `defineCachedEventHandler` (10 min, SWR), on top of the module's own 10-minute source cache; failures aren't cached. The `pages/` scan is off (`excludeAppSources: true`). A new indexable page type must be added to `buildCatalogSitemapUrls()`.
- **robots.txt**: `server/routes/robots.txt.ts` (there is no `public/robots.txt`), rules in `server/utils/robots.ts`: disallows cart, checkout, account and order pages for every country and points to the absolute sitemap URL. Those pages also carry `robots: noindex`.
- **Canonical + hreflang**: `useCountrySeoLinks()` (`app/composables/seo.ts`) on every indexable page (home, store, product, category, collection) adds the canonical link, one `hreflang` alternate per region country and `x-default` (= `appConfig.defaultCountry`), plus `og:url`. hreflang is `<locale>-<COUNTRY>` with the locale from `getLocaleFromCountryCode()`, the same mapping the region middleware uses for i18n (`pl-PL`, `en-DE`, …). Only `?page=N` (N > 1) is kept in those URLs; sorting and other params share the canonical. By-handle pages pass `() => !!data.value` so their 404 doesn't emit a canonical. Countries come from the `countries` payload the middleware loaded; nothing reads cookies, so CDN-cached pages stay shareable.
- **Product JSON-LD**: `useProductJsonLd()` renders `buildProductJsonLd()` (`app/utils/structured-data.ts`) as `application/ld+json`: one `Offer` per variant priced in the page's region (`calculated_amount`, currency, availability from `getVariantAvailability()` — the same helper the add-to-cart button uses). Never add facts Medusa doesn't provide (brand, ratings, condition). `nuxt-schema-org` isn't used: Nuxt 4.6 ships Unhead 3, so the former compatibility concern is gone; the hand-written Product/Offer JSON-LD keeps this narrow schema explicit without another module.
- **Not indexed**: cart, checkout, account and order pages (`noindex` + disallowed in robots.txt) and `/search` (`noindex, follow`: thin, endless `?q=` URLs; deliberately _not_ disallowed, so crawlers see the noindex). None of them call `useCountrySeoLinks()` or appear in the sitemap.
- **`<html lang>`**: set in `app/app.vue` from the i18n locale (`pl`/`en`), which the region middleware sets from the URL's country only — identical for every visitor, updated on client-side navigation. Not via `@nuxtjs/i18n`'s `useLocaleHead()`: it needs a `language` on every locale and logs a missing-`baseUrl` warning on every render with this `no_prefix` setup.

### Directory layout

- Imports use root aliases, never relative paths: `~/` for `app/` (also from `tests/`), `~~/` for the project root (e.g. `~~/server/...`). ESLint enforces it (`no-restricted-imports` in `eslint.config.mjs`, for `app/`, `server/`, `tests/`; dynamic `import()` is not checked). Details: `.claude/skills/nuxt-vue-architecture/SKILL.md` -> `## Imports`.
- `app/pages` — file-based routes, all nested under `[countryCode]`.
- `app/components` — organized by domain (`cart`, `checkout`, `product`, `order`, `collection`, `store`, `auth`, `app`), with further subfolders for compound UI (e.g. `checkout/address`, `checkout/payment`, `cart/item`).
- `app/composables` — one file per domain (`cart`, `category`, `checkout`, `cms`, `collection`, `country`, `customer`, `filters`, `order`, `payment`, `product`), plus `not-found` shared by the by-handle pages and `seo` (canonical/hreflang, product JSON-LD). These call into `app/services` and/or `app/repository` rather than Medusa directly (see above).
- `app/services` — `*.service.ts` business-logic layer between composables and repositories (cart, category, cms, collection, customer, order, payment, product). See the repository → service → composable note above for which ones actually have callers.
- `app/repository` — `*.repository.ts` data-access layer; `api.repository.ts` provides the shared `useMedusaClient()` + error-handling wrapper the other repositories (product, category, collection, country, order, payment, cart, customer) build on; `stripe.repository.ts` is the Stripe.js counterpart; `cms.repository.ts` is the Payload counterpart (see Payload CMS integration above) — it calls the `server/api/cms` proxy with `$fetch`, not through `apiRepository()`, since that wrapper is Medusa-specific.
- `app/utils` — pure helpers (`price`, `product`, `address`, `country`, `link`, `payment`, `percentage-diff`, `homepage`, `seo`, `structured-data`), auto-imported by Nuxt, plus `capture-error` and `sentry` (see Error reporting). `seo.ts` is also imported by the sitemap source in `server/`, so it imports its own dependencies explicitly.
- `server/api` — Nitro route handlers for `products`, `categories`, `collections`, `customers`, `regions`, `cms`; only `customers/**`, `regions` and `cms` are currently wired up to `app/` (see above). `__sitemap__/urls` feeds `/sitemap.xml` (see SEO).
- `sentry.client.config.ts`, `sentry.server.config.ts` — Sentry init for the `@sentry/nuxt` module; they must stay at the project root (see Error reporting).
- `server/routes/robots.txt.ts` — `/robots.txt` (see SEO).
- `server/utils/handler.ts` / `server/types/medusa-error.ts` — shared error-wrapping for API routes.

### Key modules (`nuxt.config.ts`)

`@nuxtjs/medusa` (Medusa SDK integration, `server: true`), `@nuxt/ui` (with `colorMode: false`), `@nuxt/image`, `@nuxt/eslint` (stylistic rules enabled), `@nuxtjs/sitemap` (pulls in `nuxt-site-config`; see SEO). Nuxt 4.6.3-compatible releases are used for Sitemap 9.1, Image 2.2, ESLint 1.17, i18n 10.6 and Sentry 11.10. `@nuxtjs/medusa` remains at 1.2.0, its latest published release (it depends on `@nuxt/kit@^3.17.3`); `pnpm build` succeeds with it on Nuxt 4.6.3. `@nuxt/ui` remains at 3.0.0 to keep this issue from expanding into its major v4 component/API migration: Nuxt UI is used in 54 Vue files, and the v4 guide documents renamed/removed components and form behavior changes. Its v3 build succeeds on Nuxt 4.6.3; migrate UI separately with visual review. Stripe is integrated via `@stripe/stripe-js` using `runtimeConfig.public.stripeKey`, only through `stripe.repository.ts`; the review step's payment flow (card, BLIK, Przelewy24 redirect and return) lives in `useCartPayment()` (`app/composables/payment.ts`). `@nuxt/icon` (installed by Nuxt UI) puts only the `lucide` and `flag` collections into the server function; every other icon must appear as a literal name in the source so the client-bundle scan picks it up. An icon name built at runtime from another collection won't render unless that collection is added to `icon.serverBundle.collections`. Don't enable `i18n.bundle.dropMessageCompiler`: with it every server render fails with `unhandled node type: 0`.
